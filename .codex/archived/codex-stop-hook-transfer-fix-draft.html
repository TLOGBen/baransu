合併發現

高Runtime 驗收責任錯置

兩位 reviewer 一致指出：transfer 只負責封裝轉換與原樣複製，無法證明 seal-guard.sh 在 Codex Stop lifecycle 會阻擋。將「主要驗收責任」放在 transfer，會讓錯誤腳本在 transfer 全綠時照樣發佈。

建議：runtime 契約歸 test-seal-guard-hook.sh；transfer 測試只驗 hooks.json/env translation、script bytes preservation 與生成內容完整性；mirror-check 驗 generated drift。

高Codex block payload 未釘住 reason

計畫只寫 decision:block，但 Stop 的 block payload 必須同時有 reason。若照字面只輸出 decision，解析階段即可拒絕。

建議：把 acceptance 固定為 exit 0，輸出 {"decision":"block","reason":"$MESSAGE","systemMessage":"$MESSAGE"}，不得同時保留 continue:false；Claude stderr + exit 2 不變，測試逐欄斷言。

高真實 CLI lifecycle 測試沒有執行環境契約

make test 會無條件執行所有 shell suite。若直接把 G11 換成 codex exec，普通 CI 會受 binary、最低版本、登入、網路、模型、hook trust 與 timeout 影響；若靜默 skip，又失去必過 regression。

建議：保留 G11 為離線、確定性的 exact-payload regression；另設非預設的 Codex CLI lifecycle target/job，明列最低 CLI 版本、暫存 CODEX_HOME、認證與 trust 來源、timeout，並斷言兩次 Stop 及第二次 stop_hook_active:true。

高Canonical 文件範圍不足

只改 transfer 文件仍會讓 seal-guard-hook.md 與 hook header 保留錯誤的 continue:false 契約，重新生成後錯誤文字會繼續進入 mirror。

建議：明列更新 canonical plugins/baransu/skills/seal/references/seal-guard-hook.md 與 plugins/baransu/hooks/seal-guard.sh 註解，再 regenerate mirror。

高漏掉 distributed version bump

修正與 mirror regeneration 若維持 3.1.6，已安裝使用者可能繼續取得 cache 中的舊內容。

建議：先 bump authoritative plugin manifest，同步 root marketplace metadata，再由 transfer 產生同版 Codex manifest，最後跑 distribution metadata gate。
