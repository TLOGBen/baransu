# optimization — decompose, transform each part into a kind, then the instrument, the proof, and the re-check

> Shared by every skill asked to make something better — faster, smaller, cheaper, fewer:
> `$baransu:think` (the 借鏡 step), `$baransu:hypothesis` (solving for a design, `../hypothesis/SKILL.md` §3,
> which `$baransu:draft` hands a protocol choice to) and `$baransu:review` (`principles/performance.md`), and
> reached from `modeling.md` whenever a model shows a cost the user named. `modeling.md` §1
> names a problem's class for a design argument; this file owns what to do once the request
> is "optimize it".
> Cue for every user-facing line: 「對人陳述時用白話」.

The default this corrects: asked to optimize, the model reaches for the local trick it already knows — a cache, a loop rewrite, a heuristic — without saying which kind of problem it is, what the best possible answer is, or how it knows the new version still does the same thing. Every optimization here starts from a model and answers, in order: **how it splits into mathematical sub-problems**, **what each sub-problem can be transformed into and which kind that is** (the table), **whether they combine** (§2), **which instrument**, **what proves it is optimal or how far from optimal it is**, and **how correctness is re-checked**. Cost may be approximated; correctness never is.

## 1. The twelve kinds

A request is usually several sub-problems, each transformed into one of these kinds (a graph problem inside a streaming pipeline is two); §2 steps 3–5 decompose it and choose per part.

| # | Kind | The sign | Instrument | What proves it (optimum, bound, or error) | Correctness re-check |
|---|---|---|---|---|---|
| 1 | Logic (boolean) | a condition, guard, feature-flag matrix or circuit with many terms; the same truth table written several ways | truth table → Karnaugh map (≤ 4–5 inputs), Quine–McCluskey / Espresso (more), BDDs; don't-care states from what callers can actually pass | prime-implicant cover is minimal for two-level form; the term and literal count before and after | equivalence check of old and new: exhaustive over ≤ ~20 inputs, otherwise SAT on the miter (old ≠ new must be unsat) |
| 2 | Discrete (combinatorial) | counting, choosing, arranging, packing bits, modular arithmetic, "how many ways" | counting arguments, inclusion–exclusion, pigeonhole, generating functions, bit manipulation, number-theoretic identities | a counting argument or pigeonhole lower bound matched by the construction | brute force on small sizes against the closed form |
| 3 | Linear algebra | loops over arrays or matrices, many dot products, fitting, projections, "compress this data" | vectorize, reorder for locality, factorize (LU / QR / Cholesky), least squares, SVD / low-rank, sparse formats | normal equations / convexity (least squares is a global optimum); Eckart–Young (truncated SVD is the best rank-k approximation); condition number for how much accuracy is lost | compare with the naive version within a stated tolerance (`modeling.md` § Relative vs absolute tolerance) |
| 4 | Reduction (P vs NP) | "find the best subset / order / assignment", search that blows up with size | reduce to a named problem (`modeling.md` §1): in P → its exact algorithm; NP-hard → exact on small instances (integer programming, SAT/SMT), approximation, parameterized (FPT) on a small parameter, or a special structure that makes it easy | the reduction itself, in the right direction (to a known-hard problem shows hardness; from it to a solver shows solvability); for an exact solve, a zero optimality gap | the solver's answer checked by the problem's own feasibility test; a design choice by the model checker (`../hypothesis/SKILL.md` §3) |
| 5 | Algorithmic | a known shape — repeated subproblems, greedy choice, linear constraints, local improvement | dynamic programming (recurrence + table size), greedy (exchange argument / matroid), LP and relax-and-round, approximation algorithms, local search | DP: the recurrence's correctness; greedy: the exchange argument; LP: the dual certificate, optimal when the gap is 0; approximation: its proven ratio | brute force on small inputs; the stated ratio checked against an exact solve where one fits |
| 6 | Topological | anything that can be recast as a graph or a topological space and improved through its structure: (A) things that depend on each other — order, what blocks what, cycles; (B) the shape of a system or network — what connects to what; (C) any other problem whose answer lives in connectivity, cycles, holes or cuts — a state space, a configuration space, the shape of a data set | (A) topological sort, critical path, strongly connected components, minimum feedback arc set (NP-hard: exact small, else heuristic); (B) spanning structures, hub vs mesh, placement by cut and distance; (C) the recast itself (nodes, edges, simplices), then its invariants: connected components, cycle basis and first homology, cuts and separators, planarity and embedding, persistent homology for the shape of data | (A) the critical path is the lower bound on sequential steps; (B) MST cut property; for placement, the cut or distance objective's bound; (C) an invariant gives the bound — an undirected graph has b₁ = \|E\| − \|V\| + c independent cycles, so leaving a forest takes at least b₁ edges; a separator's size bounds every partition — and the same invariant computed before and after the recast shows it kept what matters | (A) every dependency still precedes its dependent (a check over all edges); (B) the requirements (reachability, redundancy) re-verified on the new shape; (C) the answer mapped back to the original problem and checked there, not only on the graph |
| 7 | Graph | shortest route, how much can flow, who matches whom, conflict-free assignment, connectivity | Dijkstra / Bellman–Ford / BFS, max-flow / min-cut, bipartite matching, MST, coloring (NP-hard), TSP (NP-hard) | max-flow = min-cut; König's theorem for bipartite matching; cut property for MST; for NP-hard ones, a bound and its gap | the property re-checked on the result (paths valid, flow conserved, matching disjoint) |
| 8 | Complexity (time and space) | it gets slow or big as input grows; nested loops over the same data; memory that grows with history | asymptotic analysis, amortized analysis, better data structures, memoization, space–time trade-offs, a known lower bound (comparison sort Ω(n log n)) | the complexity class before and after, and a lower bound showing nothing asymptotically better exists, when one is known | measure at several sizes: the slope on a log-log plot confirms the class; the median of N runs against the noise floor (`modeling.md` § Median of N) |
| 9 | Mathematical model | an objective with constraints over continuous quantities — capacity, cost, latency, a tunable parameter | write the model (`modeling.md` §2), then: convex → solve, the KKT conditions are the certificate; non-convex → local optimum stated as local; reformulate for a tighter relaxation (the constraints that define the space belong in it) | KKT / duality for convex problems; the sensitivity of the optimum to each assumed input | the optimum re-run against measured inputs, not only the assumed ones |
| 10 | Streaming | one pass, unbounded or huge input, memory far below the data size, an answer needed now | reservoir sampling, Count-Min sketch, HyperLogLog, Misra–Gries heavy hitters, sliding windows, exponential histograms; selecting the best k items in one pass (a submodular objective under a cardinality limit): threshold sieves over a geometric grid of guesses, reaching 1/2 − ε, while beating 1/2 in one pass needs memory linear in the input, with the grid size set by the per-item budget | the sketch's (ε, δ) guarantee: error ≤ ε × total with probability ≥ 1 − δ, at the memory it costs; for selection, a ratio proof whose lemmas are checked as the code runs | replay a recorded stream and compare against the exact answer; the observed error within the stated ε |
| 11 | Robust (min–max) | must hold in every scenario — every delay, failure or arrival — and the worst scenario should be as good as possible | simulate the rules on every scenario (finite) or a scenario generator with a stated scope; the objective is the worst case; a relaxation small enough to search exhaustively — a subset of the scenarios, a clairvoyant dispatcher, fewer actors once every plan restricted to them is shown valid and no worse — for the lower bound | every scenario passes, and a lower bound from the relaxation that some scenario reaches | the plan broken once per rule is caught in some scenario; the bound one step tighter is infeasible |
| 12 | Several objectives | several goals ranked against each other, or traded off — "as few X as possible, then as few Y" | lexicographic: optimize each level in order and lock its optimum as a constraint for the next; a trade-off curve: the ε-constraint method, point by point; a weighted sum only when the problem is convex | ranked: each level's optimum proven (gap 0) with the levels above it locked; a curve: each point non-dominated — for integer objectives, the earlier one step tighter makes the later one worse or infeasible; otherwise the augmented ε-constraint method | a valid but worse vector refused as best; each level tightened by one infeasible |

Reading of row 6: every problem that can be recast as a graph or a topological space belongs here, and is improved through what the structure keeps — order (A), shape (B), connectivity, cycles and cuts (C); the named graph algorithms the recast often lands on are row 7. Structural topology optimization in mechanical engineering (finite elements, SIMP) is a continuous model despite its name: row 9.

## 2. The route

In this order, every time; a step that does not apply says so in one line — except step 7, which applies whenever anything was changed.

1. **Model it first, whatever was asked.** Write the mathematical model of the thing before deciding anything about it (`modeling.md` §2: variables, objective, constraints, measured against assumed). The model is what the later steps classify and cut; a request answered without one is answered about the code's surface, not its structure.
2. **Is optimization asked?** Only when the request asks for better — faster, smaller, fewer, cheaper, the best — or the model shows a cost the user named. Otherwise the model serves the request as it is and the route stops here. An asked optimization with no measurable target gets one: what is measured, on what input, what number counts as done. Measure it now (kinds 3, 8, 9, 10: on real or recorded input, with its spread). Fix the correctness tolerance now too, from what the user needs (`modeling.md` § Relative vs absolute tolerance, with its `why`): step 7 judges against it, and it is never widened afterwards to let a new version pass.
3. **Decompose.** Ask how the model breaks into mathematical sub-problems, by how the objective and the constraints hang together, and write the answer as a tree — the whole, its sub-problems, and what ties them:
   - **Separable** — the objective is a sum over parts and no constraint spans two parts: optimize each part alone; the sum of the parts' optima is the optimum, and the parts' certificates together are its proof.
   - **Ordered** — parts depend on each other without cycles: solve in topological order (row 6), each part with the earlier ones fixed; the result is optimal only when no later part's choice would have changed an earlier one's — state whether that holds, and when it does not, report the result as a bound, not an optimum.
   - **Coupled** — a few shared variables or constraints tie the parts: split by a coordination method — Lagrangian relaxation (price the shared constraint, solve the parts, adjust the price), Benders decomposition (fix the shared variables, solve the rest, cut), or alternating optimization — and report the bound the method gives and the gap between it and the answer found. Local optima per part, pieced together, are not a global optimum.
   - **Not splittable** — every part touches every other: it is one sub-problem, solved whole at a size the instrument can handle.
4. **Transform each sub-problem, and choose its optimization.** For each leaf of the tree, ask what it can be turned into that is easier to solve or to prove — recast as a graph or a topological space (row 6), reduced to a named problem (row 4), relaxed from discrete to continuous (row 5), linearized, an exact answer replaced by a sketch (row 10), a closed form found (row 2) — then name the kind the transformed form falls in, and from the table its instrument, what proves it and how it is re-checked. A transformation counts only with what it keeps written beside it: the invariant the answer depends on, or the error it admits; one that loses what the answer depends on solves a different problem. A sub-problem with several possible transformations lists them all, and step 5 chooses.
5. **Can they apply together, and why.** Optimizations of disjoint sub-problems compose — each applies on its own part. Two transformations of the same sub-problem compete — keep the one with the tighter proven bound, and say which was dropped and why. One sub-problem's result feeding another's input (a streaming sketch feeding a graph search) composes only when the error the first admits stays inside the tolerance the second needs; carry that error through and say so.
6. **Solve.** For each part (or the whole): find the best possible before the better — the lower bound, the relaxation's optimum, the information-theoretic limit; if the current version is already at the bound, say so and stop, 「已經是最佳，證據是 X」 is a complete answer — where "the bound" is the whole problem's, or every part's only when the split keeps the optimum (separable, or ordered with no later part changing an earlier one): parts of a coupled split, or of an ordered one whose later parts would change earlier ones, can each sit at their own bound while the whole does not — then apply the instrument and write its proof. **Optimal** is said only with a zero gap — the result meets the best possible, shown by a certificate. A ratio, a positive gap or an error bound says how far from optimal the result is, and is reported as exactly that, never as optimal; an optimum claimed without a zero gap is a guess.
7. **Put it back together and re-check.** Recompose the parts, re-check correctness of the whole by each row's own method against the tolerance fixed in step 2 — the parts can each be right and the whole wrong where they meet — then measure again. A faster answer that is different is a bug, not an optimization: it is not handed over, and the route goes back to step 6. Only a version that passes this step is handed over, with what step 6 proved about it.

## 3. Present it

To the person, per `modeling.md` §3: the model in one picture, which kinds it is and whether they combine, how it was split and why that split keeps or loses the optimum, how far the old version was from the best possible, how far the new one is, and what proves it — one sentence each. The derivation goes in the plan or an appendix line.
