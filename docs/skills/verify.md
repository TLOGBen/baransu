## `/review`

Claude Code：`/baransu:review`　Codex：`$baransu:review`

**用途**　派一個乾淨 context 的 reviewer 獨立審查任何產出，只讀不跑。問題的定義是「有一個地方跟改動對不上」，分三種：說了相反的話、該寫的沒寫、該給的沒給。每個問題附兩段引文。三題（做到了沒、多做了什麼、做小了沒）一定會回答；不改目標；乾淨的 review 也是有效的 review。

**什麼時候用**
- 任何模型產出之後——程式、計畫、主張——想要獨立重驗。
- 目標必須具體：一個產物、一段 diff，或直接引用的一句主張。
- 觸發語：看一下、看看、幫我看、check 一下、review 一下、take a look at X。

**運作方式**　先釘住目標、需求與範圍 → 預設派一個全新 reviewer：它用指令輸出（git log、blame、grep、CI 紀錄）列出改動改了哪些事實、每個事實還出現在哪裡，再逐處打開讀一次、每一處都給判定（成立／不成立／不確定）；判「成立」要寫出正向理由，至少附一個 file:line 加原文，證明它寫了什麼、拿到了什麼——「沒說相反的話」不算；拿不出來的就是「不確定」；問題的定義是「偏離原則」（偏離需求或寫下來的合約也算），每個問題一行表頭 `<principle file #n>：<影響>　嚴重程度 N　信心 高|中|低`（N 為 0～5），量表與信心層級只寫在 `principles/index.md` → 原則分兩階段載入：決定要看哪裡的（需求、證據、影響範圍、單一來源）在列清單前就載入，其餘走到每一處、碰到什麼才載入（有哪些原則、各自什麼時候載入，見 `references/principles/index.md`）→ 報告。加 `--full`（或說「完整審」；改動會寫入、刪除、搬移資料、重試、並行、跨信任邊界、橫跨兩個以上模組（同步維護的鏡像副本不算），或之前的 review 找到嚴重程度 3 以上的問題時也會自動開；主機跑得了別家模型時，verifier 用跟 reviewer 不同家的模型）時，改由主 session 列位置、reviewer 逐處讀，再派一個 verifier 核對每個問題的兩段引文，也逐項重讀「排除」附的證明，並確認或調整每一項的嚴重程度與信心。預設模式的 reviewer 只要回報了資安問題，也會自動補派 verifier 核對那一輪的所有問題，所以資安問題造成的 NOT PROVEN 都經過第二位讀者核對。全程不修改、不執行目標；要跑才能確認的地方也算「不確定」，那一行寫成「coverage lost: needs X」交給作者。

**產出**
- 繁中 review 報告：載入了哪些原則、每個位置的判定、每個問題的表頭（原則、影響、嚴重程度、信心）、兩段引文與五段鏈（現象／影響／根源／基石／驗證）、三題各一行（做到了／多做了／做小了；說不準的寫「不確定」）、獨立性聲明、剩餘限制；報告尾巴兩份一行一項的清單：「不確定」（拿不出成立證據、也還證明不了問題的地方，以及要跑才能確認的 coverage lost，每項寫出怎樣才能定案）與「排除」（提出過、後來判成立的候選，以及 verifier 丟掉的 finding，各附理由）；有不確定、或只有嚴重程度 0～2 的問題，最多 PARTLY PROVEN；有嚴重程度 ≥3 的問題、或紀錄顯示宣稱範圍內的失敗，就是 NOT PROVEN；結尾判定由印在報告裡的規則算出——PROVEN／PARTLY PROVEN／NOT PROVEN——再加「若只能改一處」與一行「{N} 項問題（嚴重程度 ≥3 的 {M} 項）、{K} 項不確定」。
- 零 finding 加上明確範圍，就是完整結果。
- 需要保存時寫到 `.claude/review/<slug>.md`（`/ship` 會歸檔）。

**不適用**
- 審「使用者專案」的 agent 配置與 AI 可維護性 → `/health`
- 找根因 → `/hunt`

**非互動驅動**　`loop=drivable`。

## `/hunt`

Claude Code：`/baransu:hunt`　Codex：`$baransu:hunt`

**用途**　從症狀追到根因：選對觀測層、log 二分法定位，指到 file:line 才動手修。

**什麼時候用**
- 有 bug、報錯、崩潰，或「為什麼失敗」。
- 觸發語：排查、查查、查 bug、追問題、查問題、找 bug、報錯、崩潰、狩獵、定位根因、bisect、為什麼失敗、debug、what's wrong、not working、why broken、fix error、hunt the bug。

**運作方式**
- 先挑對觀測工具：playwright、MCP db、LSP、logs、靜態分析。
- 靜態讀碼先開入口追控制流再 grep 名字，先找資料再找誰碰它；每句主張給 file:line 或說「不知道」。
- 以 `🎯HUNT-id` 標記臨時探針，確認或排除每個假設後才碰程式；確認後探針全部移除。
- 修之前先做呼叫鏈分析與測試矩陣；修復跨多檔時切片，每片實作 → `/review`。
- 特殊模式：Fast Path（瑣碎 bug）、Scope Blast、Bisect（版本對時第一批推測從 delta 來）、Repeated Regression；無法在本機重現時改用回報者探針。
- 三個假設都失敗時改出交接報告，不硬修。

**產出**
- 繁中成功報告（根因／修復／確認方式／測試矩陣／迴歸守護）或交接報告，狀態為 已解決／已解決（附帶條件說明）／受阻。
- 案件檔 `.claude/hunt-report/HUNT-YYYY-NNN.md`。

**不適用**
- 主觀的 UI 品味問題 → `/ui`
- 「值不值得修」的價值判斷 → `/think` 存廢判決（Kill / Keep / Pivot）

**非互動驅動**　`loop=assisted`。

## `/prove-it`

Claude Code：`/baransu:prove-it`　Codex：`$baransu:prove-it`

**用途**　你說的不算，證明它。照使用者的方式把 app 實際跑起來，證明「說有問題的地方真的有問題」（例如 `/review` 的發現、bug 回報），也證明「說完成的地方真的完成」（修好了、做好了、測試過了）。留下這一版的執行紀錄，`/review` 會拿它當證據。

**什麼時候用**
- 觸發語：證明它、跑跑看、實際跑一次、真的修好了嗎、prove it works。
- `/review` 列出問題，想確認是真的；或宣稱完成，想親眼看到它能動。

**運作方式**　把每個宣稱寫成一句跑得出結果的話（問題：觸發條件與錯的結果；完成：動作與對的結果；時序：寫明時間點）→ 釘住版本（commit、工作目錄有沒有改動）→ 用專案的執行食譜（`.claude/prove-it/recipe.md`；沒有就先從 repo 建一份：啟動、健康檢查、操作、證據、清理，加功能地圖，並先實跑一次）→ 健康檢查後逐項照使用者的路徑操作，記下動作、結果狀態與副作用；時序類的宣稱會故意把壞的順序做出來；數字類的宣稱（變快、變慢、延遲、哪個選項快）照七個問題跑：瓶頸在哪、兩邊都調校過沒、有沒有超過物理上限、有沒有出錯、每邊至少五次交替跑、佔整條路徑多少、工作真的有做嗎，紀錄附次數、範圍與瓶頸 → 每項判「證實／推翻／無法到達」→ 只關自己啟動的東西，證據保留。對外有副作用的步驟（送訊息、部署、付款、寫共用資料）先問。

**產出**
- 繁中報告，結尾一行「{P} 項證實、{D} 項推翻、{U} 項無法到達」。
- 紀錄：`.claude/prove-it/records/<short-sha>-<slug>.md` 與證據檔。
- 食譜與功能地圖：`.claude/prove-it/recipe.md`、`.claude/prove-it/features/`；`--maintain` 定期保養；沒打也會自動保養這次要用到的那部分：功能或形式化檢查涵蓋的檔案在上次確認之後改過，就先保養它再跑。
- 形式化檢查：宣稱是「所有順序、所有輸入都成立」（狀態機、重試、取消、並行、parser、溢位）時，跑一次只能抽樣，另建形式化檢查放在 `.claude/prove-it/formal/<area>/`。依問題選工具：順序問題用 model checker（預設 TLA+），程式對所有輸入用程式層驗證器，該語言沒有驗證器就對真的程式產生大量輸入，所有大小都要成立才用證明。每條性質要先在故意弄壞的版本上失敗過，模型每一步都對得上一行程式，寫明邊界與假設，記下同步的 commit；`--maintain` 讀過同步之後的改動，判斷是模型過時還是程式真的壞了。

**不適用**　只讀不跑的審查 → `/review`；找根因 → `/hunt`；寫或修測試 → 照 `_shared/tdd.md` 實作。

**非互動驅動**　`loop=assisted`。由 `/loop`、cron、Workflow 這類 driver 驅動時，在本機啟動、建食譜、操作都不停；碰到本機以外的副作用，只有驅動指令事先授權、並點名那個動作與對象才做，否則該項記為「無法到達」並回報需要你。

**來源**　改寫自 pstack 的 `create-verification-skill` 與 `maintain-verification-skill`；數字類宣稱的跑法改寫自 `benchmark-checklist`（cursor/plugins，MIT）。
