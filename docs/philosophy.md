# 理念：バランス

> バランス。動手前先想，做完後驗證。

[← 回文件索引](README.md)

## 由來

市面上的 skill 很多，用起來卻都不對勁：要嘛什麼都不管，模型照自己對需求的理解一路跑；要嘛儀式太重，改一行也得先填五張表才能動工。第一次嘗試是自製的 `everything-cli`，做完才發現走到了另一個極端——token 燒得快，每個小任務都要先過七道關卡才碰得到程式碼。有用，但太重。`baransu` 是第二次嘗試。

## 核心原則

平衡不是妥協，重點是知道**什麼時候**可以輕、什麼時候不准輕。小任務不需要三輪對焦；重要的決策不能省略思考。工具配合任務的形狀：小任務走輕量路徑，大任務走完整規格——不反過來逼任務遷就工具的流程。每個 skill 都有清楚的觸發界線：什麼可以省、什麼一定要做。

自 v2.1.0 起，這條線寫成可驗收的理念（現為六條）。每條都綁一個倉內機制錨點——無錨點的條款不入冊，錨點存在性由結構驗證器（`scripts/verify-skills.py`）把關。

## 從根部修、值不值得三問

平衡也關乎修正**落在哪一層**。一個失誤要在最高、能讓它不可能再發生的那一層處理：先是結構（skill 能做什麼、不能做什麼——review 從不改目標、ship 只在被點名時動手、Authorization PAUSE 不能走預設），其次是 skill 要達成的原則，最後才是它必須遵守的規則。結構就能解決的事卻寫成規則，等於替一個設計決定付利息。

任何一行要加進 skill 之前，三個問題決定值不值得：（1）本倉有沒有證據——一次真實翻車，或一條已經貼在症狀上的守衛——證明既有條文或流程做出了錯的判斷；（2）這個改動是不是用更合身、更清楚的條文**取代**那一條——不一定更多、不一定更少——而不是在旁邊再加一條守衛；（3）對著今天的模型預設，這一行還會不會改變行為——每條指令都有半衰期，路由衰減最快，目標、紅線、證據與授權最慢。三問有一問不過，就不收。機制錨點：`/evolve` 的 finding 鏈（現象 → 影響 → 肇事條文 → 來源 → 基石）與它的減法閘。實例：8.0.0 退役 contract 與 seal，不是因為它們錯了，而是半衰期到了——對一個模型已經不再犯的問題用了太大的力。

## 任務不遷就工具

小任務不硬上全套，大任務不偷走輕量路。實際怎麼分流，見 [三頻段路由](routing.md)。
