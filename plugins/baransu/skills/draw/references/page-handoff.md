## Handing a page to /ui

/draw stays the only entry point and delivers the finished page; /ui designs it. This hand-off applies to diagram, map, film and component alike. After every piece passes its own lane check and critique rows (a map needs a passing `finalize` receipt with browser checks run):

1. Write `docs/ui_brief.md`: who reads the page and what they must understand, the order of the ideas, the page validation widths for desktop and phone, each piece's path, its form, lane-check evidence, SHA-256 hash, required controls, size and theme behaviour, its one-line point and its caption, the facts the page text may use (from `docs/brief.md`), the page file name `<page-name>.html` in the output folder (distinct from every piece's `<name>.html`), and the browser rule, the same as /ui's § Browser checks: any screenshot or check of the page runs either in the user's real Chrome through Claude in Chrome (the user's own profile, when that tool is connected) or through a Chromium started by `<skill>/scripts/motion/browser.mjs` `launchChromium()` — in practice `verify-page.mjs`, `perf-check.mjs` and `grab.mjs` — never a Playwright MCP, agent-browser or a bare `chromium.launch()`. The `verify-page.mjs` and `perf-check.mjs` runs in step 4 below are still required: they are the page's recorded evidence.
2. In a non-interactive run, deliver the checked pieces and this brief without invoking /ui; follow `references/loop-pauses.md`. In an interactive run, in the same turn, invoke /ui through the Skill tool (`baransu:ui`) with that brief: the piece paths and a short summary of the request. Do not stop, do not ask the user, and do not start a subagent by default — /ui ships in the same plugin and the main session holds the request's context. Only when the build has already filled the context (for example after a long film) may the hand-off go to a subagent, and then it gets the whole of `docs/ui_brief.md`.
3. /ui designs the page's look, layout and text and embeds the pieces (an iframe per piece, or their markup and script lifted in); each piece keeps its own look. A finalized map is embedded by iframe referencing the exact checked file; never lift, rewrite or restyle its runtime. Hash every piece again after page assembly and record equality in `docs/ui_brief.md`; if draw revises a piece, rerun its lane check before replacing the hand-off hash. /draw does not restyle the page.
4. Run `verify-page.mjs` and `perf-check.mjs` on the assembled page as well (several heavy pieces on one page must respect § One heavy figure at a time), and record the result in the completion report, which says that the page path ran (pieces + /ui).

5. At the desktop and phone widths required by the page brief, operate the embedded map itself: zoom, pointer drag/pan and node information where available. Record actions and observable state changes, along with page and frame overflow. Screenshots support appearance only; `verify-page.mjs` and `perf-check.mjs` do not prove these interactions. Use the seeded browser helper for the interaction driver too. If any check cannot run, report it as unverified, never passed.
