Opus 5.5 動態設計片場

這篇長文拆解了 Opus 5.5 上市後一週內爆紅的「一句 prompt 做出動態影片」。結論只有一句：prompt 只佔影片的 10%，其他 90% 是 harness，也就是渲染引擎、參考素材、節拍，以及讓模型回頭看自己畫面的評審迴圈。

頁面裡的六張動畫圖都用了文章教的方法：每一格畫面都是時間 t 的純函數。按暫停後拖動時間軸，任何一格都能一模一樣地重現。

一分鐘看懂

  1. 模型不輸出影片，它寫程式。一個 seek(t) 函數畫出任意時刻的畫面，再由無頭瀏覽器逐格截圖、ffmpeg 合成 MP4。
  2. 「一句話 one-shot」是真的，但只夠測試你的環境。爆紅作品背後多半是上萬字的 brief、skills、API key，以及好幾個小時的自主執行。
  3. 擺脫 AI 感靠三件事：給參考（點名一種風格勝過描述它）、寫狀態清單、用彈簧取代固定緩動曲線。
  4. 聲音不是後製。先量出節拍或用程式合成音樂，把轉場、狀態變化和音效都釘在同一張節拍網格上。
  5. 關鍵習慣是讓 Opus 看自己的畫面。渲染靜態格、打分、修最差的 3 項，直到每項 ≥ 8 才全片渲染。最後把整條流程包成一個 skill。
01–02

原理：模型寫的是程式

Opus 5.5 只吐得出文字，生不出 MP4。這波每一支影片，都是 Opus 寫的一段程式，再由別的工具把程式轉成畫面。

核心技巧是決定性。Opus 寫一個 draw(t) 或 seek(t)，給它任何時間點，它就畫出那一格的精確畫面。15 秒 60fps 就是無頭瀏覽器呼叫 900 次、截 900 張圖，再交給 ffmpeg 接起來。整個流程不依賴計時器，所以每次渲染結果都相同，要修改只要改一行再重渲染。

兩條路線

  • Route A（Opus 的預設）：零依賴，一個 index.html 加上 Playwright 和 ffmpeg。Tommy Rossi 發現就算環境裡裝了 Remotion 或 HyperFrames，Opus 還是選這條。想用框架要在 prompt 裡明講。
  • Route B（框架）：Remotion（React）適合系列、模板、資料驅動的影片；HyperFrames（HTML + GSAP）適合習慣用網頁思考的人。兩者都有現成的 Claude skills。

只有 Claude Code 這種有 shell 的 agent 能渲染、聽聲音、看自己的影格。聊天介面寫得出動畫，但做不到這個回饋迴圈，而這個迴圈正是「第一版很普通」和爆紅作品的差別。

Effort 的建議：小修和重渲染用 medium，新片用 xhigh，開頭 3 秒要撐起一次產品發表時用 max。文中每一支爆紅的 one-shot 都跑在 xhigh 或 max。

03–06 · 10

Prompt 的四個層級

作者把九篇爆紅貼文的 prompt 排成一道梯子。越往上 prompt 越長，但真正變多的是右邊那欄：模型手上能用的素材、規格和流程。

L1 · 一句話 showreel 
make a dynamic 15-second motion graphics video that shows
what an incredible motion designer you are, like it's your
showreel for a résumé. go all out.
  • 「résumé showreel」指定了一種規則明確的類型：快剪、每鏡一招、最強的放最前面。
  • 「你是多厲害的動態設計師」讓模型當主角，它只需要秀技巧，沒有內容會出錯。
  • 「15 秒」短到能一次做完，又夠放 6 到 8 個鏡頭；「go all out」是疊在 xhigh/max 上的加乘。

弱點是 athemeroy 資料集說的「brief contagion」：幾百個人用同一句 prompt，做出的片子彼此押韻。一句話測的是引擎，測不到點子，因為裡面根本沒有點子。

L2 · 指向你的品牌

Tony Dinh 一年前花 1,000 美元以上請人做的發表影片，這次不到 30 分鐘。他只多寫了三行：產品網址、「用真實的產品截圖、logo、素材」、「一定要有音樂」。Opus 會自己去網站抓素材。

  • 同一品牌固定用同一個 session：渲染器、音效合成、輸出流程都已經在了，第二支更快。
  • API key 放 .env，在 prompt 裡只寫變數名，別把真 key 貼進會截圖的 prompt。
  • 加一個會說話的吉祥物（ElevenLabs 配音），achxvi 現在就拿這個接案。
L3 · 參考 + 狀態清單

沒有參考時，Opus 會退回預設長相：置中標題、漸層背景、所有東西淡入。給參考的三種方式：

  • 一張影格：附圖，講明要拿什麼（配色、字體、顆粒）、不拿什麼（主題）。
  • 一支影片：叫它用 ffmpeg 每 0.5 秒抽一格，先逐鏡描述節奏再寫程式。
  • 你的圖庫：先產出 style_guide.md。自己的作品集是別人抄不走的參考。

@twoclipping 的 UI morph（90.7 萬瀏覽、1.9 萬收藏）用 XML 規格寫成：<inputs> <direction> <structure> <build> <gotchas> <start>，描述的是逐拍的狀態清單，沒有任何氛圍形容詞。

L4 · 導演 brief

Donald 口述 5 分鐘就去睡了，Claude 跑了 12 小時，交出 142 秒的 MV，有 210 萬次瀏覽。brief 約 9,500 字元，Pip 機器人那支有 19,000 字元。骨架都一樣，寫的是一整個劇組的分工：

  • 一句話的片子、參考、工具與 key、角色聖經、分鏡節拍表、畫面文字規則、帶關卡的流程、評審迴圈、交付清單。
  • Generate-then-trace：先用 Seedance 2.5 生成有角色與物理的基底鏡頭，再由 Opus 用 JS 整支重畫一層蓋上去，觀眾只看到程式畫的那層。
  • PDoom repo 的子代理模式：先寫 ANIMATION_GUIDE.md 統一風格，再讓子代理平行做 9 個章節。
07–08

引擎：讓動態看起來很貴

便宜的動態沿著固定曲線從 A 走到 B；貴的動態有質量感，會加速、微微超出目標、再回穩。爆紅的 morph 影片全都指定用 closed-form 彈簧，因為它的公式直接算出任一時刻的值，seek(t) 還是純函數。

多數人漏掉的技巧：一個值多次換目標時（游標、容器寬度），不要重啟彈簧，而是每次變化疊加一條從那一刻開始的彈簧。動作保持連續，而且要畫第 812 格時，不必先模擬第 0 到 811 格。

Snappy UI按鈕、開關、前緣
Default卡片、容器、鏡頭
Heavy大字、3D 物件、logo
Playful吉祥物、貼紙，明顯超出

文章提供的 track() 就是這個疊加公式，只有四行：

export function track(t, keys, k = 170, d = 26) {
  let v = keys[0][1];
  for (let i = 1; i < keys.length; i++)
    v += (keys[i][1] - keys[i - 1][1]) * spring(t - keys[i][0], k, d);
  return v;
}

One shape, never cut

@twoclipping 和 @verbove 的影片都用同一個概念：整支片只有一個元素，從按鈕變成載入圈、播放器、滑桿、圖表、指令面板，一次都不剪接。游標用真實的點擊驅動每次變化，最後一格等於第一格，所以能無縫循環。

規格裡的兩個坑：不要對會被鏡頭縮放的元素加 will-change，文字會變糊；最後一格必須和第一格相同，連游標的位置和速度都要一樣，否則循環接縫會頓一下。

09

聲音：釘在節拍上

Rob Hallam 以為音樂是後製加上去的，其實不是。聲音是「AI 影片」開始有電影感的地方，作法有兩條：有現成音軌就量它，沒有就在同一條時間軸上用程式合成。

量測用 librosa 找出節拍輸出 beats.json，動畫直接讀這個檔：小的狀態變化放在每一拍，大轉場放在每小節第一拍（downbeat），音效放在量到的峰值（hits）。整體響度調到 −14 LUFS。

實例：@oozn 的賈伯斯 2 分鐘傳記片，配樂在 Node 裡合成，每個剪接點都鎖在 120 BPM；Vox 的〈small print〉用 Python 合成音樂，再對著渲染結果逐秒打磨。文章還附了一支 sfx.mjs，用程式直接合成 click、whoosh 等 UI 音效寫成 WAV。

11

評審迴圈：讓 Opus 看自己的畫面

Opus 5.5 看得懂圖片，所以它能檢查自己渲染出來的東西。這一個習慣，就是爆紅作品和「感覺有點普通」的作品之間的分界。

@mablesjoseph 那支水彩短片講得很坦白：163 次模型呼叫、約 6¾ 小時（親自操作約 1½ 小時）、API 牌價約 34 美元、6,270 萬 token（96% 是 cache read），完全不是 one-shot。迭代是方法本身，不代表失敗。

文章給的五個檢查都是一行 ffmpeg：

  • 接觸印樣：每秒 2 格、6 欄拼成一張圖，一眼看完整支片。
  • 連續格條：快速動作前後 12 格連排，抓跳格和重疊。
  • 手機測試：縮到 360px 寬，看字還讀不讀得到。
  • 循環檢查：首尾相接播兩次，盯接縫。
  • 決定性檢查：同一段渲染兩次，md5 必須相同。

評審 prompt 的重點是要它「當嚴厲的動態導演，不要當驕傲的作者」，並且主動找這些問題：切換時文字重疊、物件滑動而非緩動、角落標籤和外框、置中漸層鏡頭、縮放後模糊的文字、沒有事情發生的空拍、循環接縫的頓點。修完只重渲染受影響的秒數。

文章建議把這套規則寫進專案根目錄的 CLAUDE.md，每支片都自動套用：

# Motion studio rules

## Render contract
- Every film is a pure function of time: `window.seek(t)` paints frame t.
- No CSS transitions, no setTimeout, no requestAnimationFrame in render mode,
  no state carried between frames. Seeded noise only (mulberry32), never Math.random.

## Look
- Banned defaults: centered title on gradient, everything fading in,
  corner labels and frame borders, glow on UI chrome, generic particle bursts.
- Every 2 to 4 seconds something new must happen on screen.

## Loop before you show me anything
1. Render one frame per beat as a contact sheet and LOOK at it.
2. Score it 1-10 on: hook in first 2s, readability at phone size,
   motion quality, variety, brand accuracy, sound sync.
3. Fix the 3 worst problems. Repeat until every score is 8+.
4. Only then do the full render.
12

規模化：一條時間軸、一個 skill、一門生意

  • 所有比例來自同一條時間軸。場景寫在 layout 函數上，不寫死像素，請 Opus 平行渲染 9:16、1:1、16:9。每個比例要重新排字和 UI，不要把 16:9 直接裁成直式。
  • 打包成 skill。文末的 motion-reel SKILL.md 把流程收成 8 步：抓素材、寫 style guide、量或合成音樂、在節拍網格上寫分鏡並等確認、用彈簧寫 seek(t)、至少 3 輪評審、渲染並混音到 −14 LUFS、交付。之後只要一句 /motion-reel for [URL], 20s, vertical, reference ./refs/frame.png。
  • 變成收入。achxvi 同一週就開始接案：音樂、任意風格的吉祥物、產品功能、結尾優惠、任何語言、最多改 3 次。Tony Dinh 的 1,000 美元是定價錨點；有了 skill 和評審迴圈，一個下午就能交件。

我的讀後看法

  • 價值在整理和可直接用的程式碼。這是一篇整理文，也是 Substack 的導流文。它把 9 篇爆紅貼文的 prompt 模式收在一起，並附上幾段能直接用的程式：render.mjs、spring/track、beats.py、sfx.mjs、ffmpeg 檢查指令。
  • 原文看得出趕工。文中留著「Put it directly under the anatomy diagram」「Place under the brand prompt」這類排版備註，部分嵌入推文和說明的順序對不上。瀏覽數、1,000 美元、12 小時這些數字都是原 po 自述，沒有獨立驗證。
  • Route A 的程式碼不適合長期維護。Tommy Rossi 自己說產出是滿是 magic number 的義大利麵，程式碼只是產物。要做系列或長期維護，用 Remotion 加上一份共用的 lib/motion.js 比較實際。
  • 成本要先算。xhigh/max 加上數小時的自主執行，再加上 fal、ElevenLabs 等外部額度。Donald 的 brief 直接寫了「把 Max 方案額度全部用掉」和約 2,000 美元的 fal 額度。
  • 最划算的起手式：先用 L1 確認 Playwright 加 ffmpeg 的環境能跑，然後直接跳到 L3，也就是一張參考影格、一份狀態清單、加上評審迴圈。

跟你的工作流程怎麼接

導演 brief 的關卡（plan → stills → animatic → full pass → polish → audio → render）加上評審迴圈，就是「動手前先想清楚、做完要驗證」，跟 baransu 的 governance 精神同一路。

如果想把它收進 common-dev，文末的 motion-reel 結構（先收集輸入、管線、硬規則）很適合做成一個通用 skill：render.mjs、beats.py、motion.js 放在 skill 目錄裡，用 ${CLAUDE_PLUGIN_ROOT} 引用。這是可以另外評估的選項，不是這篇文章的結論。
