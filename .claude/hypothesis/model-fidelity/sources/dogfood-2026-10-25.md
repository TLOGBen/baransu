## 卡點

### 0. 載到的 skill 不是 repo 的版本（環境問題，不是 skill 本身的問題）

`Skill` 工具載入的是 `~/.claude/plugins/cache/baransu/baransu/8.22.0`，repo 已經是 8.26.0。兩版的 §3（先讓人看懂再確認）和 §5（圖畫在哪）不一樣。在 baransu repo 裡做 dogfood 時要改讀 repo 的 SKILL.md，不然測到的是舊版。

### 1. 舊程式沒地方放：放進 `sources/` 之後，一對應回原檔就永遠過期

- 規則端是某個 commit 的程式，工作區裡已經換成新程式了。`sync.files` 只對工作區算雜湊，沒辦法引用 `<commit>:path`。
- [sources.md § Sources that move](../../plugins/baransu/skills/hypothesis/references/sources.md) 只處理網址跟會被 `/ship` 封存的目錄，沒處理「舊 commit 的檔案」。
- 照那一節的做法（複製進 `sources/`，再用 `sync.originals` 對應回原檔），[hypothesis-status.py:193-196](../../plugins/baransu/skills/hypothesis/scripts/hypothesis-status.py) 會發現原檔（現在是新程式）跟副本不一樣，從發布那一刻起就判成 `stale`。`--maintain` 也修不好，因為不一樣正是重構本身造成的。
- 能走的路：複製進 `sources/`，但**不寫** `sync.originals`，讓副本自己被引用、被算雜湊。能用，但文件沒寫。
- `hypothesis.json` 的 `roles` 一個角色只能放一個 `<path>`，這次舊端有兩個檔案、新端有三個。

### 2. 「程式當規則端」要怎麼比，`--satisfies` 沒有說

[sources.md:27](../../plugins/baransu/skills/hypothesis/references/sources.md) 說兩邊都可以是程式，但比對方式只寫了「每一步都對得到規則允許的一步」。這是 refinement mapping 的寫法：要寫一個函式，把新模型的每個狀態對應到舊模型的狀態。這次寫不出來，原因很具體：新模型把 `refresh` 寫成「隨時都可能重讀」，舊模型照實寫了時間戳判斷。兩邊對使用者來說行為一樣，但舊模型內部的鎖狀態沒辦法從新模型的狀態算出來，要加輔助變數才行。這已經超出 skill 現在教的範圍。

實際改用的做法：讓 TLC 把兩個模型的完整狀態圖吐出來，各自投影到使用者看得到的東西（磁碟索引、每個行程的 view、每個操作的結果），再比較兩邊的「可達狀態」跟「會發生的變化」。這樣兩個方向一次比完，不用寫對應函式。代價見卡點 4。

### 3. 盲抽的兩個模型不一樣，差異全是建模錯誤（最重要）

兩個 agent 各自只看一個 commit，也不知道這是重構比對。兩版程式在這段幾乎逐行一樣，抽出來的模型卻有五個地方不同：

| 地方 | 舊版 agent | 新版 agent | 照程式該怎樣 |
|---|---|---|---|
| 放棄等鎖 | 只有鎖正被別人拿著的那一刻才能放棄 | 任何時候都能放棄 | 「試鎖失敗」跟「看時限」是兩個敘述，鎖可能剛好在中間被放掉。所以放棄要發生在一次失敗的試鎖之後，但當下鎖不一定還被拿著 |
| 寫入前的開關檢查 | 有，會被拒絕 | 沒放進模型 | 兩版程式都有 `_check_writable` |
| 寫入失敗 | 隨時 | 讀者開著檔案時不能改名，另外也可能隨時失敗 | 兩版一樣，都是 `with open` 加重試 |
| `refresh` 的時間戳 | 照實建模 | 改成隨時都可能重讀 | 兩版一樣 |
| 公平性 | 讀者不會永遠讀失敗 | `adopt` 不會永遠搶不到鎖 | 由建模者自己選，程式沒說 |

拿投影比對跑：

- 2 × 1：新版多 6 種變化。其中 4 種（P1 成功之後 P2 才回報 conflict）程式真的會發生，是舊模型太嚴格；另外 2 種（從頭到尾沒人拿過鎖，兩邊卻都回報 conflict）程式不會發生，是新模型太寬。
- 1 × 2：新版多 16 種（同一行程內回報 conflict，但行程內鎖會先排隊，不可能發生），舊版多 4 種（被開關檢查擋下，新模型漏了）。
- 只修正第一列和第二列之後，兩個範圍的差異都歸零。

意義：

- 我上一輪擔心「同一個 agent 抽兩邊會抽成一樣」，這個擔心是對的，盲抽確實避開了這個問題。但盲抽換來的是另一種雜訊：兩邊的抽法不同。直接比的話，26 項差異看起來都像重構弄壞了東西。
- 反過來看，**盲抽兩次再比對，本身就是抓建模錯誤的工具**。這 26 項差異裡，每一項都至少指出一個模型跟程式不符。
- 兩個模型都通過了所有安全規則，壞掉的版本也都被抓到。換句話說，skill 現有的兩道門檻（看過它失敗、看過它成功）都擋不住這種錯，因為它們檢查的是模型有沒有在認真檢查規則，不檢查模型像不像程式。

### 4. 投影比對到 skill 要求的範圍就跑不動

[formal.md § Strict, 4](../../plugins/baransu/skills/hypothesis/references/formal.md) 要求每種會同時跑的角色至少兩份，也就是 2 行程 × 2 thread。在這個範圍下，單一模型就有 350 萬個狀態，要把整張狀態圖輸出成 dot 檔，大小是 GB 等級。所以投影比對只做到 2 × 1 跟 1 × 2，這兩個範圍把「跨行程」和「同行程跨 thread」分開各測一次。2 × 2 只跑了規則，沒有做行為比對。

### 5. 「終究會結束」這類規則慢，而且結果取決於建模者選的公平性

- 「每個操作終究會結束」在 2 × 2 範圍很慢：舊版跑了 41 分鐘才守住，新版到寫紀錄時還在跑。
- 舊版 agent 第一次只用弱公平性，TLC 找到一個反例：讀者一直讀失敗、一直重拿鎖，`adopt` 永遠搶不到。它改成「讀者不會永遠讀失敗」再跑。新版 agent 選的是「`adopt` 終究搶得到鎖」。兩邊選的假設不同，這類規則的比對結果就會受建模者的選擇影響，不只受程式影響。

### 6. 新版能跑的環境，舊版根本不存在

新版的 `locks.py` 多了 POSIX 分支（`fcntl.lockf`）；舊版在檔案最上面就 `import msvcrt`，只能在 Windows 跑。新版在 Linux 上的行為沒有任何舊行為可以對照，refinement 比對在這裡根本無從比起。另外，`fcntl` 的鎖是整個行程共用一把，不是每個 fd 各一把，所以同一行程裡的互斥完全靠 `_tlock`。這次的兩個模型都沒有區分這一點（都當成 Windows 的語意）。報告裡應該把它列成「比對範圍外」，而不是默默略過。

### 7. 沒有發布：規則確認的暫停，跟「不用等我」衝突

§3 要求使用者看懂並確認規則之後才能建模，這是第一次寫入時唯一的 Input PAUSE。使用者的全域指示是「能復原的事不要停下來問」。這次規則是我照程式擬的，沒有經過使用者確認，所以只在 scratchpad 跑，沒有寫進 darkroom 的 `.claude/hypothesis/`。如果要發布，還要先解決卡點 1 的 `sources/` 寫法。

## 怎樣讓建模問題更早被發現

這次的建模錯誤是靠盲抽兩次再比對才挖出來的。現有的流程裡，沒有任何一步會發現它們，因為：

1. **兩道證據門檻只驗「規則有在檢查」，不驗「模型像程式」。** 看過它失敗，證明規則抓得到錯；看過它成功，證明模型沒有空轉。但一個比程式更嚴格的模型，兩道門檻都過得了。
2. **唯一拿模型對照真實 app 的地方（§5 交給 `/prove-it` 重播），只在規則被打破時才觸發。** 這次所有規則都守住，所以模型從來沒被拿去對照過。也就是說，**越常通過的模型，越少被檢查。**

依照「越早越便宜」排序，可以加的做法：

| 時機 | 做法 | 抓得到哪一種 | 這次能不能抓到 |
|---|---|---|---|
| 建模當下，幾分鐘 | **盲抽兩次，在最小範圍做投影比對。** 兩個看不到彼此的建模者各抽一次，在 2 × 1、1 × 2 這種小範圍比較使用者看得到的變化，有差異就回頭對程式 | 太嚴、太寬、漏步驟都抓得到 | 能，26 項全抓到 |
| §3 確認規則時 | **除了規則，也給人看模型認為「不可能發生」的事。** 例如「模型說：鎖空著的時候，不會有人回報 conflict。對嗎？」 | 太嚴（模型禁止了程式會做的事） | 能，對程式熟的人一眼就看得出來 |
| 抽每一步時 | **原子性要附證據。** 模型裡每一個「一步」引用的程式範圍，如果包含兩個以上會碰共享狀態的敘述，又沒有鎖或交易包住，就要寫明理由。formal.md 已經有這條規則，只是沒有人檢查 | 併步（這次舊模型的錯就是把兩步併成一步） | 能 |
| 模型通過之後 | **通過的模型也要拿真實執行驗一次。** 讓 app 或測試實際跑幾次，記下事件順序，檢查每一條記錄都在模型允許的範圍內（TLA+ 叫 trace validation）；同時從模型挑幾條路徑交給 `/prove-it` 重播 | 太嚴（真的跑出模型不允許的順序）、太寬（模型的路徑真實 app 走不出來） | 太嚴的部分能，前提是測試有碰到逾時邊界 |

我的建議是：先把第一列跟第二列放進 `/hypothesis`。兩者都便宜、都在建模當下就有效，而且這次都已經實際驗證過。第四列最徹底，但要能在專案裡插入事件紀錄，成本比較高，可以等真的遇到需要時再做。

## 第二次實驗：讀程式的 agent 能不能反駁「不可能發生的事」

使用者回答了「確認規則時，誰算熟程式的人」：「理論上是我 + 指派你實際看程式」。這次實驗要測的是那個「指派去看程式的 agent」到底管不管用。

做法：從舊版盲抽模型（`blind-old`）整理出 6 條它認為「永遠不可能發生」的事，交給一個全新的 agent。它只拿到程式（`94df5dd~1`）跟這 6 條，任務是「逐條去程式裡找反例」，看不到任何模型，也不知道哪條是錯的。其中第 3 條是刻意放進去的已知錯誤：「某個操作成功並放開鎖之後，另一個還在等鎖的操作就不可能再回報 conflict」。

| # | 模型說不可能 | 出題者的標準答案 | agent 的判定 | 誰對 |
|---|---|---|---|---|
| 1 | 回報成功，但變更不在磁碟上 | 做不到 | **做得到**：`rename_preset` 改成同名時 `changed` 為 False（`preset_library.py:395-397`），跳過寫檔（`:340`），照樣回報成功（`:345`）；如果磁碟上原本就沒有這一筆，結束後還是沒有 | agent |
| 2 | 回報成功後，自己行程的畫面看不到變更 | 做不到 | 做不到 | 一致 |
| 3 | 鎖放開之後，等鎖的操作不會再回報 conflict | 做得到（刻意放的錯） | **做得到**（它走的是業務上的 conflict 那條路，`:431`） | 一致 |
| 4 | 兩個行程各有一個操作回報 conflict | 做得到 | 做得到 | 一致 |
| 5 | 只有一個行程在跑時回報 conflict | 做不到 | **做得到**：`create_group` 遇到已存在的群組直接回報 conflict（`:431`），跟鎖無關 | agent |
| 6 | 被開關擋下的操作會先拿到 `_tlock` | 做不到 | 做不到（`:329` 比 `:330` 早一行） | 一致 |

98 秒、6 次工具呼叫。刻意放的錯被找到了，另外又找到兩條連標準答案都錯的地方。

**這兩條錯是我帶進去的。** 我在派給兩位建模者的指示裡寫了「操作內容抽象成把自己的 id 加進索引」、「等鎖逾時就是 conflict」。兩位建模者彼此看不到，但看到的是同一份指示，所以錯得一模一樣，投影比對完全沒反應。出標準答案的也是我，所以標準答案一起錯。讀程式的 agent 沒有拿到這層框架，就看得出來。

這帶出三件事：

1. 盲抽只讓建模者彼此獨立，不讓他們跟「下指示的人」獨立。指示裡的抽象，本身就是一個共同的錯誤來源。盲抽時，指示應該只寫範圍跟要檢查的規則，不寫怎麼抽象。
2. 「交給一個獨立的 agent 拿程式反駁」這一步，在這次真的有效，而且很便宜。它就是 `model-fidelity` 假說的前提 A2 的依據。
3. 對 darkroom 重構比對的結論要加一句限制：「行為一樣」是在「操作 = 加入自己的 id」、「conflict = 鎖逾時」這個抽象下成立。不寫檔就回報成功的路徑、業務上的 conflict，這次都沒有比到。這幾段（`rename_preset` 到 `create_group`）重構後只多了 4 行說明文字，邏輯逐行相同（文字比對確認過），但沒有經過模型比對。
