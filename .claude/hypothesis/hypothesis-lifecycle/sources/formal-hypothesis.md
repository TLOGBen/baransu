# 假說：寫下機器檢查過的系統主張，讓人看得懂，讓其他 skill 拿來用

> 第三版。這一版改掉的假設有三條。
>
> 1. 第二版把假說放在 `/prove-it` 底下，由 `/prove-it` 守住；使用者更正：`/prove-it` 是「證明它」，假說是「寫下它」，兩件事分開。
> 2. 程式改了導致假說要跟著改，也是假說自己的事。
> 3. 假說一律是形式模型，「既然是假說，就走最嚴格的路子」。

## 確認過的重述

- **要的結果**：新增 `/baransu:hypothesis`。它的工作是**寫下假說**：一條關於系統行為的主張，**一律寫成形式模型**，用機器窮舉或證明，附上白話規則和逐張加元件的狀態圖，讓人看得懂。
  - 假說是獨立的產物，有自己的目錄。
  - **輸入不限程式**：需求訪談、會議紀錄、RFP、SA、SD 文件都可以，也可以拿兩份文件互相對照（例如 SD 有沒有滿足 SA、提案有沒有涵蓋 RFP）。從文件寫出的假說，檢查的是「文件描述的流程本身有沒有矛盾、缺漏、模糊」，以及「這份文件有沒有滿足那份文件」，不是「系統真的這樣運作」。
  - 三種場合使用它：
    - `/hunt`：寫下追查需要的假說
    - 功能的「定義完成」：完成時必須成立的假說
    - `/review`：依據假說，快速找出這次改動破壞了什麼
  - 程式改了，假說的維護也歸它。
- **`/prove-it` 回到「證明它」**：拿假說去證明，不寫假說，也不維護假說。
- **觸發**：使用者主動叫用，或模型依逐條列出的 H1–H8 判斷。不能形式化的主張不算假說，繼續走 hunt、TDD 原本的作法。
- **為什麼**：模型越來越快，數學驗證是使用者最信任的證據，而且必須看懂才會信。
- **不能改變的**：三頻段不強迫升段；review 只讀不寫；不准為了通過而改弱性質或模型。
- **規模**：核心路徑，架構方向，屬於大頻段。

## Building

**可觀察的結果**：

1. **寫下**：`/baransu:hypothesis <模組或問題>` 會讀程式，跟使用者確認規則，然後交出四樣東西：
   - 一句一條的白話規則
   - 形式模型，每個動作都引用 `file:line`
   - 機器檢查的結果，附工具、版本、範圍
   - 一個自動打開的 HTML 頁：第 1 張只有正常流程，每張多一個元件，最後一張把 bug 路徑編號
   - 有反例時，附上用程式的話寫的劇本
   - 這些全部存在 `.claude/hypothesis/<area>/`
2. **使用**：
   - `/hunt`：碰到 H1–H3 類的偶發症狀，或加了 log 後行為改變，就請 `/hypothesis` 寫一份假說，再把每條反例路徑轉成探針。模型通過，不能拿來丟掉線索。
   - **定義完成**：一個功能可以宣告「完成 = 假說 X 被證明」。紅綠的確認綠燈會重跑所有涵蓋到這次改動檔案的假說。**重跑結果是「過期」就算紅燈**，並且自動交給 `/hypothesis --maintain`；維護完、重跑通過，綠燈才過。
   - `/review`：改動碰到某個假說的涵蓋範圍時，假說的每條規則都成為必答題；假說過期就回報。
3. **證明**：`/prove-it` 拿假說去證明。它用固定版本重跑模型，在真的 app 裡用強制順序重現反例，把結果寫進紀錄。涵蓋檔案在同步 commit 之後改過時，結果是「過期」，不給「通過」，並且**自動**交給 `/hypothesis --maintain`，不等人想起來。這條是生命週期模擬（`.claude/hypothesis/hypothesis-lifecycle/`）找到的路徑 ②：只寫「交回維護」、沒寫誰去叫，假說會永遠過期。
4. **文件**：`/baransu:hypothesis <文件或兩份文件>` 先用 `/read` 把 PDF、docx 轉成 Markdown，從文件抽出流程、角色、規則，寫成形式模型，然後交出三樣東西：
   - **矛盾**：兩條規則無法同時成立，附上會撞在一起的走法
   - **缺漏**：某個狀態沒有出路，或某種情況文件沒有交代該怎麼辦
   - **模糊**：文件沒寫清楚先後或歸屬，例如「核准綁的是金額還是版本」，列成要問誰的問題

   文件對照時，一份文件當規則，另一份當行為，檢查行為是否滿足規則（精化檢查，refinement）；不滿足就附上反例。圖組一樣會產出，可以直接拿去會議上跟業務方對齊。
5. **維護**：`/hypothesis --maintain` 讀同步 commit 之後的每一處改動，歸成四類：
   - 沒有影響
   - 模型已經不描述程式了：照程式更新模型
   - 承諾是刻意改的：引用證據改寫規則
   - 承諾可能被破壞了：列為 bug 候選

   更新之後，要再看過一次它會失敗，同步 commit 才往前移。

**這個設計的單一想法**：假說就是一份機器檢查過、人看得懂的系統主張，由 `/hypothesis` 寫下並維護。其他 skill 只讀它、用它、證明它，不改它。

**觸發清單**：寫在 `hypothesis/references/formal.md` 的開頭，是單一來源，其他 skill 只引用。

**不觸發**（就算出現上面的字眼也不觸發）：

- 跑一次就能確認的主張
- 單一端點上的靜態權限檢查
- 外觀、文案、文件、設定值、參數選擇
- 只有一個讀者的唯讀查詢
- 已經有一份同步中的假說，此時改成重跑它
- 明說要丟掉的原型

**嚴格的意思**（每一份假說都必須做到）：

- **真實對應來源**：模型的每一部分都引用來源。程式引用 `file:line`；文件引用段落原文和位置（檔名、章節、頁碼或行號）。來源裡不可分割的一步，在模型裡也是一步；名稱用來源自己的用詞。文件沒寫清楚的地方，不准自己補，要列成「模糊」問題。
- **先講白話**：每一條發現、反例、模糊問題，都分兩層寫。第一層用 `/huh` 的口吻，日常用語、沒有術語，讓沒碰過形式驗證的人（包括文件模式下的業務方）讀完就知道出了什麼事；第二層才放技術細節，例如 `file:line`、TLC 版本、狀態數、性質名稱。這條規則寫在 `/hypothesis` 自己的輸出規則裡，不在執行中去叫用 `/huh`。
- **同步對象**：判斷「過期了沒」一律看**涵蓋檔案的內容雜湊**，程式和文件都一樣，所以還沒存檔的改動、切換分支也看得到。commit 只用在維護：當作比對改動的起點，以及判斷原因的證據。
- **維護怎麼讀改動**：照 `/how` 的方法讀程式現在怎麼運作，用來判斷模型還描述不描述程式；照 `/why` 的方法找改動的原因（commit 訊息、ADR、計畫檔），用來判斷「承諾是不是刻意改的」。沒找到原因，就歸成「承諾可能被破壞了」。（使用者決定：why 看原因、how 看內容）
- **故意改壞的版本存進 git**：`variants/` 裡的每一個改壞版本都要提交，讓別人能重跑「看過它失敗」。（使用者決定）
- **看過它失敗**：在丟棄式的副本裡把程式改壞，檢查必須抓到。
- **看過它成功**：每條安全規則都要配一條目標可達的規則，而且要看過「拿掉一個轉移後，目標就到不了」。這是用來擋下偷懶版那種空洞規格。
- **範圍誠實**：寫明範圍、假設、沒涵蓋什麼。窮舉的結論只在範圍內成立；使用者要求「不設範圍」時，改用歸納證明。
- **發現就是發現**：程式每一步都走得到的反例，就是 bug；程式走不了的那一步，才算模型錯。
- **沒有形式化的部分都要寫原因**：每一段沒被形式化的程式或主張，都要寫成一條紀錄，共四欄：哪一段（`file:line` 或主張原文）、原因屬於哪一類、具體情況、要滿足什麼條件才能形式化，以及現在改走哪條路（hunt 的推測、紅綠測試，或不處理）。原因只能從下面幾類選：
  - **沒有工具**：該語言沒有驗證器，或工具沒安裝。寫出缺的是哪個工具。
  - **無法建模**：行為取決於模型外的東西，例如外部服務、硬體時序、時間精度。寫出是哪個依賴。
  - **超出範圍**：狀態空間太大。寫出試過的範圍和跑了多久。
  - **符合不觸發條件**：寫出符合清單裡的哪一條。
  - **沒有對錯可證**：外觀、偏好、文案。
  - **使用者決定不做**：引用使用者的原話。
  - **交給別份假說**：寫明交給哪一份假說，或哪份計畫的哪一片會做；兩者都沒寫就不算數。（使用者決定新增，2026-10-24；起因是生命週期假說裡「hunt 的探針流程」那一段，原本六類都不合）

  「無法寫成假說」這個結果也一樣，必須附上這筆紀錄；沒有原因的「沒形式化」，不算完成。

**成功標準**：

- **已知答案考題**：拿簽核三版跑 `/hypothesis`。
  - 天真版要找出三條不變式違反，每條都附編號路徑圖和 `file:line` 劇本
  - 修正版要通過
  - 偷懶版要在「看過它成功」那一關失敗
- **圖組**：每一份 HTML 頁都符合四個條件：第 1 張只有正常流程，而且不超過 7 個狀態；每張只比前一張多一個元件；bug 路徑有編號；標籤沒有變數名或動作名。
- **過期**：一份涵蓋檔案在同步 commit 之後被改過的假說，在 `/prove-it`、紅綠的確認綠燈、`/review`、`/health` 四處，都回報「過期」，沒有一處回報「通過」。
- **hunt 掛勾**：在簽核天真版的 Bug 2（撤回和核准同時按）上，`/hunt` 會從 Tool Scan 走到 `/hypothesis`，並把反例轉成至少一個 yes/no 探針。
- **單一來源**：觸發清單 H1–H8 每條都附訊號、工具、至少一個不觸發的例子，而且只寫在一個地方。
- **文件考題**：把簽核規則寫成一份短需求文件，故意埋三個問題：一條矛盾（「撤回後可重送」對上「撤回為終止狀態」）、一個缺漏（被退回後沒寫能做什麼）、一個模糊（核准綁金額還是版本）。`/hypothesis` 必須三個都找到，每個都引用文件原文；拿它跟一份滿足規則的 SD 對照要通過，拿一份漏掉財務關卡的 SD 對照要失敗並附上反例。
- **白話層**：每份假說的每一條發現，第一句都不含這些詞：活性、安全性、精化、不變式、同步點、TLC、模型、狀態空間。用簽核考題的三條違反，加上生命週期模擬的路徑 ②，各寫一次來驗證。
- **原因紀錄**：每份假說的 README 都有一節「沒有形式化的部分」，裡面每一條都填滿四欄，原因屬於上面列的某一類。模組明明落在 H1–H8，模型卻決定不寫假說時，也要在 hunt 或 review 的輸出裡留下同格式的一條。用簽核考題驗證：把「寄通知信」這一步標成「無法建模：外部郵件服務」，README 必須出現這一條。
- **其他**：`make test`、`make parity-check` 通過；Claude 版和 `codex/` 鏡像同一次變更；本地 repo 先同步到 8.15.0 或更新。

## Not building

- **非形式的假說**：一句可推翻的主張加一個測試，這種不算假說。使用者選了最嚴格的路子，hunt 的一般因果猜測和一般的完成條件，繼續走 hunt、TDD 原本的作法。何時需要：試行顯示大多數真實需求都因為「無法形式化」而落空，那時再重新考慮「可推翻就算」。
- **H7 退回性質測試**：性質測試不是形式驗證，退回去就違反「一律形式」。何時需要：同上。
- **自動呼叫 `/draw`**：`/draw` 的合約要求第一版在一小時內交付，還有評分修正迴圈（`draw/SKILL.md:34`）。`/hypothesis` 自己用 Mermaid 產生 HTML 頁並打開，做法同 `/show-me`（`show-me/SKILL.md:16`、`:128`），標籤規則借 pstack `statechart`。何時需要：使用者要可以拿去簡報的正式圖時，手動叫 `/draw`。
- **review 自己寫假說**：review 只讀不寫（`review/SKILL.md:39`），改成回報「coverage lost: needs /hypothesis」。這條不會變成需要。
- **把 `/health` 自己的檢查範圍寫成形式性質**：health 稽核的是設定，沒有狀態空間（`health/SKILL.md:13`）。health 只做兩件事：在「驗證覆蓋」那一層回報過期的假說，以及讓環境急診認得 TLC 和 Java。
- **流程編排器**：`/baransu-way` 剛在 8.15.0 退役（CHANGELOG：「全自動模式還要再想」）。
- **我不是什麼**：不是流程編排器；不是把每個任務都變成數學證明；不是讓 review 或 prove-it 去改假說；不是替代 hunt 的探針與重現。

## Approach

**為什麼這樣切**：使用者的區分很清楚：寫下是一件事，證明是另一件事。

- 8.15.0 把形式檢查放在 `/prove-it` 底下（`prove-it/references/formal.md`、`.claude/prove-it/formal/`）。這讓「證明它」的 skill 同時要建模、講解、維護，它的單一想法就糊掉了。
- 第三版的切法是：
  - **`/hypothesis` 擁有假說**：寫、畫、維護
  - **其他 skill 是讀者**：`/prove-it` 證明，`/hunt` 追查，`/review` 對照，紅綠和 `/draft` 引用
- 規則只有一本，跟著擁有者走：`formal.md` 從 `prove-it/references/` 搬到 `hypothesis/references/`。這也跟 pstack 把 create、statechart、maintain 拆開一致，而且比 pstack 多一條：證明和寫下分開。

**借鏡**：

- **航空軟體的危害分析**：HAZOP 引導詞把「風險」變成逐條清單；DO-178C 依失效後果分級，DO-333 是其中的形式方法補充。改變了什麼：觸發清單的結構。
- **需求工程的形式化需求分析**：把自然語言需求轉成邏輯規則，再用求解器檢查一致性和完整性。Amazon Science 的文章提到 Kiro 用自動推理證明需求「沒有矛盾、模糊和缺漏」（廠商自述）；文件對照則是形式方法裡的精化檢查。改變了什麼：文件輸入的三種產出（矛盾、缺漏、模糊），以及對照時的「一份當規則、一份當行為」。
- **教學設計的「逐步揭露」**：一次只多一個元件，跟 `/teach-me` §5 同源。外部裁判是使用者自己能不能用一句話說出 bug 路徑。改變了什麼：圖組的四個條件。
- **科學方法的「可證偽性」**：一個假說必須說得出什麼觀察會推翻它。改變了什麼：「看過它失敗」和「看過它成功」是假說成立的必要條件，不是加分項。

**成本與效果的模型**：

- 當 p·(1−d)·H > C_f 時，就該寫假說。H 是出一次事的損失，p 是性質被違反的機率，d 是一般測試抓到它的機率，C_f 是建立並維護假說的成本。
- 已測得：簽核模型約 150 行，TLC 不到 1 秒跑完 425 個狀態（本次實測，TLC2 2.19）。
- 寫模型的 agent 成本約幾十萬 token，是估算，未實查。
- 「一律形式」讓 C_f 的下限變高，所以觸發清單必須嚴格。H1–H3 是 d 低（測試排不出那個順序），H4–H6 是 H 高。

**成本對效果**：

**承重的前提，以及它不成立時怎麼辦**：

- **前提一**：真實的核心模組能被寫成「對得上程式、不空洞」的形式模型。如果實測常常寫不出來，結果會是大量「無法寫成假說」，那時要重新考慮被否決的「可推翻就算」。
- **前提二**：從模型推出的圖組讓人看得懂。如果看不懂，改用 pstack 的 from-chart 方向：先畫圖給人確認，再生成模型骨架。
- **前提三**：讀者 skill 守得住「只讀不改」。這由結構保證：只有 `/hypothesis` 會寫 `.claude/hypothesis/`，其他 skill 只引用它的檔案與命令。

**相容性**：8.15.0 已經在用 `.claude/prove-it/formal/` 的專案，`/hypothesis --maintain` 第一次執行時會提議搬到 `.claude/hypothesis/`。搬之前，`/prove-it` 照樣讀舊位置。**同一個區塊在任何時刻只能存在一處**：舊位置還有這個區塊時，`/hypothesis` 不在新位置寫同名區塊，要求先搬。搬家是一次完整的移動，不是複製。8.15.0 的檢查沒做過「看過它成功」，也沒有原因紀錄，所以**不論搬了沒有**，都標成「嚴格檢查未完成」，不能拿來宣告完成；要先維護一次補上。只寫「搬過來的才要補」是不夠的：生命週期假說的維護找到一條路徑，`/prove-it` 直接讀還沒搬的舊檢查、回報通過，就宣告完成了。使用者既有的工作流程不會斷，所以是 minor 版號，不是 major。

**接受的邊界**：

- 觸發仍有判斷成分。
- 模型不等於程式，只能靠 `file:line` 加上重跑來縮小差距。
- 工具缺少時，結果是「無法寫成假說」。
- 窮舉的結論永遠附上範圍。

**試行**：這個計畫是暫定的。第一片是試行，挑風險最高的前提一。

## Key decisions

1. **可以把假說放在 `/prove-it` 底下（第二版），選擇給它自己的 skill 和目錄**：寫下和證明是兩件事；擁有者只有一個，讀者可以有很多。反轉條件：試行顯示 `/hypothesis` 和 `/prove-it` 總是被一起叫用、從不分開。
2. **可以接受「可推翻就算」，選擇一律形式**：使用者明確選擇最嚴格的路子。代價寫在 Not building，被否決的選項是前提一失敗時的退路。
3. **可以讓 `/hunt` 繼續把一般的因果猜測叫做「假說」，選擇改名為「推測」**：「假說」在 baransu 裡只指一件事，機器檢查過的形式模型。hunt 的一般猜測（`hunt/SKILL.md:142`、`:332`）改叫「推測」；推測落在 H1–H3 時，交給 `/hypothesis` 寫成假說。這會改到 hunt 給使用者看的輸出用詞，屬於 minor。術語寫進詞彙表的事，交給 `/baransu:domain-modeling`。
4. **可以只靠規則「記得重跑」，選擇用結構保證**：涵蓋檔案在同步 commit 之後改過，假說的結果就是「過期」，四個讀者都會這樣回報。依據是 pstack 運作模型窮舉出的漂移路徑。
5. **可以只要求「看過它失敗」，選擇再加「看過它成功」**：依據是偷懶版模型通過了全部三條安全規則。
   - 第 1、3、4 條改變了規則的位置、hunt 的用詞，以及 `/prove-it` 的判定語意。曾提議記成決策紀錄（ADR），使用者決定不寫（2026-10-24）；這些理由留在這份計畫與 `.claude/draft/hypothesis-skill.md`。
