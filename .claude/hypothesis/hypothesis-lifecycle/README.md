## 發現（先白話，後細節）

**① 程式改壞了，系統還說沒問題。**
細節：沒有過期拒答時，程式改動引入 bug 之後，`/prove-it` 用停在舊版的模型重跑，回報「通過」。3 步。

**② 大家都說「過期了」，然後就沒人處理，事情永遠做不完。**
細節：維護只能由人叫用，又沒有人保證會叫，三個讀者都回報「過期」之後就停住，「完成」永遠到不了。已修正：讀者回報過期時，自動交給維護。

**③ 如果綠燈只是提醒，改壞的程式照樣會被放行。**
細節：`GreenMode = "warn"` 時，程式改動引入 bug，綠燈重跑看到「過期」卻放行。3 步。這就是選「算紅燈」的理由。

**④ 如果新舊兩份可以同時存在，會有人去看沒人管的那份。**
細節：`AllowBoth = TRUE` 時，舊目錄還在就寫了新的一份，`/prove-it` 讀到舊的那份。3 步。這次舊的剛好還是對的；程式一改，它就是路徑 ①。

**⑤ 還沒搬家的舊檢查，也能被拿來宣告「做完了」，雖然它從沒檢查過「做得到」。**
細節：`MarkMigrated = FALSE` 時，`/prove-it` 直接讀舊目錄回報通過，馬上宣告完成；那份檢查從沒做過「看過它成功」。3 步。計畫原本只要求「搬過來的」要補，已改成不論搬了沒有都要補。

**文件檢查**：

- **矛盾**：無。
- **缺漏**：原本的「交回維護沒寫誰叫」（②）和「舊檢查能直接拿來宣告完成」（⑤），都已補進計畫。
- **模糊**：原本兩個（綠燈遇過期怎麼算、新舊並存以誰為準），使用者都已回答。

## 沒有形式化的部分

| 哪一段 | 原因類別 | 具體情況 | 要什麼才能形式化／現在走哪條路 |
|---|---|---|---|
| 「模型通過，不能拿來丟掉線索」（hunt） | 交給別份假說 | hunt 的案件流程不在這份模型裡；原本交給第三片另寫一份，第三片完成時沒有寫，交接還沒完成 | 另寫一份假說 hunt-case；現在走 hunt 自己的紅綠紀律與 /review |
| 「在丟棄式的副本裡把程式改壞」 | 無法建模 | 取決於模型外的程式內容 | 改走已知答案考題 |
| `--maintain` 遇到「承諾是刻意改的」要停下來問人 | 沒有對錯可證 | 「承諾是不是刻意改的」只有人能回答；第二片把它做成 `--maintain` 的 Input 暫停 | 不形式化；由使用者回答 |
| 圖組「讓人看得懂」 | 沒有對錯可證 | 「看懂」是人的判斷 | 改走使用者回饋 |
| 從計畫抽出規則的忠實度 | 無法建模 | 取決於有沒有讀錯原文 | 每條規則附原文，交給使用者確認 |
