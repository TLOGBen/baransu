# 假說：TLA+／TLC 加上實際跑，能不能完整取代 unit test

- **使用者要拿它做什麼**：決定 baransu 的流程（CLAUDE.md 三段路由、`_shared/tdd.md`）要不要拿掉「照 tdd.md 紅綠」，改成 TLA+／TLC 加上實際跑（sandbox）。
- **理想**：每個會傳到使用者手上的缺陷都在發布前被抓到，花的力氣最少；不寫一個從來沒抓到東西的測試。
- **主張**：
  - A：這個 repo 出現過的每一個程式缺陷，TLA+／TLC 或實際跑至少一個抓得到（對每一個缺陷）。
  - B：先紅後綠的測試之後變紅時，抓到退步的不到一半。
  - C（使用者追加）：與其寫 unit test，不如把一開始就知道的對錯寫成 lint。
- **已證明**（往上推，範圍內）：50 個程式缺陷裡，R1 一個都沒被打破（一般讀法與嚴格讀法都 0）；實際跑抓得到 45 個，另 5 個只在無法強迫的順序出現，TLA+ 都抓得到。unit test（kit）看不見的有 10 個，全是平台前提錯（桌面版怎麼畫、模型怎麼輸出），都是實際跑抓到的。B：紀錄裡 140 次測試變紅，抓到退步 2 次（1%）。C：kit 抓得到的 40 個裡，lint 能在寫入時擋下的 6 個（15%）。
- **最好可能**（往下壓）：比理想低，兩個論點（第二推導提出，我核對過）：(1) 真 app 在這個帳號造不出來的輸入（別的方案、API key 沒有用量資料、平台少見的狀態），只有餵假資料的測試碰得到；歷史上沒有實例。(2) 每次改動的回歸網：字串解析這類輸入空間很大的程式（刪除預覽、範圍比對、合集解析），TLA+ 把字串抽象掉、而且檢查的是模型不是程式（`format.md`：「TLC checks the spec, not the code」），`--quick` 要 1,379–1,576 秒；實際跑每種寫法要一個真 session；作者自己的維護紀錄寫「程式的改動用 282 個測試把關」。
- **差距**：還能改進，性質是「已知的缺口」：A 在「找出缺陷」上範圍內成立，但「每次改動確認沒弄壞別的」對字串解析類程式只有 unit test 負擔得起（W4 不算成本，所以 R2 嚴格說沒被打破，實務上被打破）。
- **規則確認**：R1–R3 與讀法 W1–W4 使用者 2026-11-04 確認（W1 = b，W2 = a＋使用者協作，W3 = 過半，W4 = 不算成本）。
- **涵蓋的對象**：這個 repo 10/01 起的程式缺陷（`git log`）、`.claude/hypothesis/lint-mod-state/`、`lint-cards/` 的出錯路徑、2026-11-04 這個 session 在 sandbox 找到的缺陷；8.0.0（`b505b8ae`）之前改過 `tests/` 的 148 個 commit，與 8.46.0 的 kit 測試結果。
- **描述的版本**：baransu 8.46.5（`69634f3b`），2026-11-04。
- **定稿雜湊**：criteria.md `6fe44fbc5956…`、check.py `7f78902b1236…`、build_tests.py `645972b18570…`、corpus.csv `2b033102acb9…`、tests.csv `d9cb56eebeea…`。
- **重跑**：`cd model && uv run build_tests.py && uv run check.py`（約 10 秒）。檢查器說得出不：把 `corpus.csv` 的 MS-P3 改成 `tla,no,no,yes` 會報 R1 被打破（`uv run check.py <改過的資料夾>`）。
