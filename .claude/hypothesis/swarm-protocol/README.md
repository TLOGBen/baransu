## 交互機制（模型 `model/Swarm.tla` 的設計）

- **蜜蜂只留檔案，不改看板**：收工前寫回報檔（完成附證據／完成沒證據／問蜂后／問使用者／環境壞了），然後結束；中途消失就什麼都沒留。宿主會通知蜂后。
- **蜂后不靠記憶**：只讀看板、回報檔和蜜蜂是否還活著；壓縮後把每件「進行中」的任務對照回報檔與蜜蜂是否還在，已結束的當作剛收到通知處理。
- **等回答的蜜蜂不佔名額**：卡住的任務仍佔著路徑，但不佔名額；回答後用空名額叫醒同一隻蜜蜂。
- **路徑被佔而開不了工，看板寫明在等誰**：等待鏈接到使用者。
- **問使用者的事只問一次**，同時有幾題就合成一則；問完蜂后照樣處理其他任務。
- **閒著不准停**：有空名額又有能開工的任務就立刻派；能開工的比空位多時，先派後面依賴鏈最長的。
- **環境壞了**：蜂后修好、寫成 lint 檢查，叫醒同一隻蜜蜂，不扣嘗試；第二次算失敗。
- **防坑**：消失先叫回一次；同一次嘗試第二次卡住或第二次消失都算失敗，換新蜜蜂；最多兩次，之後是缺口；依賴缺口的跟著變缺口。

## 範圍

範圍 1（`MC.tla`）：三件任務、兩個名額；t1、t2 共用路徑 a，t3 依賴 t1、由使用者中途加入；每件最多兩次嘗試。範圍 2（`MC2.tla`）：三件互不相干的任務、兩個名額；每件一次嘗試（只問名額會不會被佔光，兩次嘗試時 10 分鐘跑不完）。活性：兩件任務、一個名額，一組有依賴（t3 依賴 t1、中途加入）、一組互不相干；兩次嘗試（三件任務時 10 分鐘跑不完）。每隻蜜蜂每次最多一個背景工作；蜂后被壓縮最多一次（壓縮不改任何持久狀態，一次和多次等價）。

拆細：一件太大的任務在開工前拆開，或第一次因太大失敗後拆開；模型裡等同中途加任務（已涵蓋）；原任務被取代的收尾沒有建模。

不建模：蜜蜂做出來的東西好不好（交給 `/review`）、git 層的實際檔案衝突（只把路徑歸屬當資料）、花費、選哪個模型、找事做與拆任務的判斷、依賴成環（以 skill 文字禁止）、審查後的修正輪（以 skill 文字限一次）。
