# tradeoffs — 我們接受 X，換到 Y

## 採用的

1. **我們接受 plugin 多一支 Python 腳本（`hypothesis/scripts/hypothesis-status.py`），換到讀者一行就能回答四個問題，不用判斷。**
   先例：`hunt/scripts/hunt-search.py`、`scripts/verify-skills.py`，所以不是新依賴。腳本不在時一律是 `broken`，不會變成「沒有假說」或「通過」。

2. **我們接受新鮮度用「涵蓋檔案的內容雜湊」判定，而不是計畫寫的「同步 commit 之後有沒有改過」，換到未提交的改動、切分支、rebase 都看得見，而且切回原內容又會是 fresh。**
   紅綠綠燈和 review 最常讀的正是**還沒 commit** 的工作目錄；只比 commit 會在這兩個最常見的呼叫點漏掉改動。commit 仍然留著（`sync.commit`），只給 `--maintain` 當 diff 的起點。計畫的語意沒變：「來源在同步點之後改過 → 過期」，只是「改過」用內容判定。

3. **我們接受檔案層級的粗顆粒（涵蓋檔案裡改一個註解也會過期），換到判定完全機械、沒有誤判成通過的可能。**
   代價由 `--maintain` 的「沒有影響」出口吸收：不用改模型，重跑一次就發佈。改用函式或行號範圍的雜湊，行號一移就全錯，而且要解析每種語言。

4. **我們接受「讀者看到的狀態」不存在磁碟上、每次現算，換到沒有任何一份「通過」會過期。**
   存下來的只有「在這些雜湊下結論是 X」。這讓「過期不會假裝通過」從一條讀者要記得遵守的規則，變成結構：腳本在不新鮮時直接把結論印成 `?`。

5. **我們接受沒有索引檔，每次讀都掃 `.claude/hypothesis/*/hypothesis.json`，換到少一份要保持一致的狀態。**
   area 的數量在一個 repo 裡預期是個位數到幾十個；掃描成本可忽略。

6. **我們接受 watch pattern（對守護狀態寫入的 regex）由寫假說的人在讀程式時寫下，換到「新的程式寫入了被守護的狀態」也會讓假說過期。**
   這是只看涵蓋檔案雜湊永遠看不見的漂移：新增一個 `auto-approve.ts` 直接寫 `status = 'approved'`，涵蓋檔案一個字都沒改。regex 會漏，但漏的方向是「沒看見新寫入者」，跟沒有它一樣；不會讓假的通過變多。

7. **我們接受證據完整性在讀的時候也檢查（`proved` 沒有 seen_failing／seen_succeeding → `draft`），換到偷懶版模型在任何讀者那裡都不會顯示為通過，就算寫入端漏檢。**
   重複了一次寫入端的檢查；但這是兩個不同的時點（publish 時、讀時），手改 JSON 只會被讀時那次擋下。

8. **我們接受讀者在 `stale` 時只能做固定動作（回報、交回維護），換到讀者不需要知道怎麼判斷「這次改動影不影響模型」。**
   那個判斷只有一個主人：`--maintain`。紅綠綠燈因此在改了涵蓋檔案時必然要先跑一次 `--maintain`——這是成本，也是計畫要的「沒有一處回報通過」。

9. **我們接受 `hypothesis.json` 與 README 有重複（規則句子、範圍），換到讀者只讀機器格式、人只讀 README。**
   單一來源是 JSON：README 的那幾節是從 JSON 產生的，README 本身的雜湊也在 `sync.artifact` 裡，手改 README 會讓 area 變 `draft`。

10. **我們接受精化對照的方向寫在旗標上（`<行為> --satisfies <規則>`），換到不會把兩份文件的角色搞反。**
    兩個位置參數（`A B`）要讀者記住哪個是規則；旗標把方向寫成英文句子。

11. **我們接受 `loop=assisted`（偏離 brief 寫的預設 `not-drivable`），換到讀者看到 `stale` 時能自動叫起 `--maintain`，假說不會永遠過期。**
    理由：計畫在我讀完第一版後更新了（生命週期模擬路徑 ②：只寫「交回維護」、沒寫誰叫，就永遠到不了完成）。代價是多一份 `references/loop-pauses.md`、`_shared/loop-contract.md` §4 多一列、Gate 10 要過。停點只有一個（承諾是刻意改的，要人給證據），而且不能預設放行。寫下（首次）仍需要人確認規則，在無人模式下直接回報「需要人確認」。讀者那一側（腳本）本來就無人可跑，不受影響。

## 考慮過、放棄的

- **索引檔 `INDEX.md`／`index.json`**：反查快，但多一份狀態、兩個寫入者會漂移。刪除測試顯示它只是轉手（見 `seams.md`）。
- **把讀者狀態存在檔案裡（`status: proved`）**：讀者最省事，但它就是那份會「過期還說通過」的狀態本身。
- **只用 `sync.commit` 判定（`git log <sync>..HEAD -- <files>`）**：計畫原文。漏掉工作目錄的改動，而那是紅綠和 review 的主場；舊位置 legacy 才保留這種讀法。
- **讀者自己讀 README 判斷**：沒有腳本、純 Markdown。每個讀者各自實作新鮮度判斷，六份規則，必有一份寫錯；而且 LLM 讀 Markdown 表格時把「發佈時：成立」讀成「成立」的風險正是這個拉力要消除的。
- **函式層級的涵蓋（symbol + 範圍雜湊）**：過期更準，但要跨語言解析；行號移動造成大量假的 `stale` 或、更糟，對錯位置的雜湊。
- **讓 `/prove-it` 的重跑結果回寫 area**：讀者省一步，但違反「只有 `/hypothesis` 寫」；而且重跑通過不代表模型仍描述程式（模型不讀程式）。
- **腳本放 `_shared/scripts/`**：讀者路徑短一點，但 schema 的擁有者是 `/hypothesis`，schema 和讀它的程式碼要一起改，所以放在擁有者目錄。
- **出口碼只有 0／1**：讀者得再解析輸出才分得出「沒有假說涵蓋」和「有、但沒過」；紅綠要把前者當綠、後者當不綠，所以分成 0／10／1／2。
