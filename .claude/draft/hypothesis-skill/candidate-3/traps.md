# traps — 這個形狀會怎麼壞掉

1. **adapter 的細節漏進核心。** SKILL.md 或 `formal.md` 開始寫「TLC 的 cfg……」「`file:line` 要……」，接縫就形同虛設，下一個工具又要改核心。
   - 防線：核心只准提 `ports.md` 的表單名稱。可以在結構驗證器加一條：SKILL.md 和 `formal.md`（除了觸發表的「預設工具」欄）不准出現任何 `tools/` 或 `sources/` 檔名以外的工具名。

2. **共用表單變成最小公約數。** 為了讓 `witness` 和 `path` 共用一種格式，硬把 Kani 的具體輸入塞成「狀態序列」，圖就會說謊。反方向也一樣：表單一直加欄位，最後每個 adapter 都要填一堆跟自己無關的欄位。
   - 防線：新增欄位前，要指得出兩個 adapter 都會用到。只有一邊需要的資訊，留在 adapter 內部。

3. **假想的 adapter。** `kani.md` 在這台機器上還沒跑過。如果它沒通過考題就上架，H7 的結果看起來是「證明了」，其實是一份沒驗證過的指南在說話。
   - 防線：§ Admitting an adapter。沒收錄的一律回「沒有工具：adapter 未收錄」。

4. **讀者重跑時寫進產物目錄。** TLC 預設在當下目錄寫 `states/`，cargo 寫 `target/`。`/prove-it` 照 README 的指令一跑，就違反「只有 `/hypothesis` 寫 `.claude/hypothesis/`」。
   - 防線：工具 port 的 § Run 規定暫存輸出導到 `$HYP_TMP`。關卡紀錄加一條：跑完之後 `<area>/` 底下的 `git status` 必須是乾淨的。

5. **過期只看得到「涵蓋檔案被改」。** 新增一個檔案也去寫同一份狀態（例如新的 webhook handler 直接改 `status`），`git diff -- covers` 看不到，腳本會說「沒過期」。
   - 這是結構保證的盲點：腳本算出來的過期只是下限。
   - 補救有兩層：`--maintain` 的 § Diff since sync 會搜尋新的寫入者；`/review` 把每條規則當成必答題，會從改動那端撞到它。
   - 要在 `formal.md` § What readers may conclude 寫明這個限制。

6. **對照方向弄反。** 「SD 有沒有滿足 SA」，如果把 SA 當成行為，精化檢查會在錯的方向上通過或失敗。
   - 防線：`--against` 那一份固定當規則；規則確認時第一行就寫「規則：SA；行為：SD」，讓使用者確認。

7. **文件轉檔不穩定。** markitdown 換版本，同一份 PDF 轉出不同的 Markdown，引用的原文就對不上了。
   - 防線：過期只看原檔雜湊。轉檔器改了，只會記錄 `snapshot_sha256` 不同，引用仍然以快照為準。
   - 剩下的風險：從新版抽的原文，跟舊快照的斷行不一樣。

8. **「從文件抽規則」本身讀錯。** 這是計畫的承重前提之一。這個形狀沒辦法解決它，只能讓它被看見：每條規則都附原文，規則確認那一步給人看。試行時量錯誤率，常出錯就改成逐條勾選。

9. **area 的粒度。** 一個模組上有兩個主張，到底是一個 area 兩組規則，還是兩個 area？
   - 粒度太粗，一個 area 的模型越長越大，狀態空間爆掉。
   - 粒度太細，同一份 `covers` 出現在很多 area，review 每次都要回答很多重複的題目。
   - 規則：一個 area 對應一個模型。共用狀態的主張放進同一個模型。

10. **搬家把「通過」降成「草稿」，讓使用者以為壞了。** 結尾那一行要說明原因：「搬自 prove-it/formal，尚缺『看過它成功』與圖組」。

11. **組合型 `pair` 的兩邊同時過期或只過期一邊。** 維護時只更新一邊，精化對應就可能悄悄失效。
    - 防線：`pair` 的 § Diff since sync 合併兩邊的改動；只要有一邊動了，就重跑整個精化檢查，不只重跑那一邊。

12. **adapter 數量看起來很多，讀者嚇到。** 從 SKILL.md 到實際做法要跳四個檔案。
    - 防線：第 0 步明講每次只載入綁定的那些檔案。adapter 的節名固定，讀過一個就會讀全部。
    - 如果試行發現 agent 常常讀錯 adapter 或漏讀 `ports.md`，就該把 `ports.md` 併回 SKILL.md。

13. **Codex 鏡像。** `$CLAUDE_SKILL_DIR/../hypothesis/scripts/...` 這種跨 skill 路徑，在 Codex 的目錄結構裡不一定一樣。鏡像那一片要用 `codex-skill-transfer` 查證；查不到的話，讀者改用 repo 根目錄的相對路徑。
