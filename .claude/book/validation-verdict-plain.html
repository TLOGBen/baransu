墊底翻身記——驗證輪判決白話版

同樣的人馬再上場，只改一件事：把合約寫死。然後上一輪的最後一名，追平了冠軍。

01這輪在測什麼

上一輪實驗留下一個尷尬結果：花最多錢、開最多 agent 的完整流程組合墊底，什麼流程都不給的單模型裸做反而排在前面。診斷出的病因不是流程本身，是規格太鬆——像驗收房子時合約只寫「牆壁應該好看」，監工看到牆歪了，翻合約也找不到條文退件，只能寫個「建議改善」放行。

上一輪的審查員正是如此：它看到了 bug（畫面印出自相矛盾的章節編號），但條文只要求「訊息裡要有某幾個字」，bug 沒違反條文，按規矩只能放行。這一輪把同樣的人馬（Opus 規劃、Sonnet 實作）再派上場，只改合約的鬆緊。

02只改三件事

  • 條文寫到能退件。以前寫「要顯示遷移結果」；現在寫「訊息必須一字不差是『進度已遷移：{章節名}』，不准出現任何從編號算出來的數字」。監工看到違規，條文就是尚方寶劍。
  • 固定的東西用抄的，不准用背的。上次一個正規表達式經兩手轉抄，簡體「节」默默消失，整條功能靜默失效。這次規格放一個原文照抄區，寫的人複製貼上，驗的人逐字比對。
  • 審查員的工作說明書換掉。四個具體動作：逐條對合約、專掃沒測試保護又給使用者看的東西、檢查兩個介面有沒有各寫各的、常數逐字比對。外加新規矩：合約沒禁止不是放行的理由——看到真 bug 但條文管不到，那是合約的 bug，一樣退件。

03墊底翻身記

同樣的 Opus 加 Sonnet，這次 20 條驗收全部有測試釘死、零 bug、架構滿級。盲評做了破壞測試——故意把六個功能各弄壞一次看測試會不會叫——六次全部被抓到。測試不是裝飾品，是真的在站崗。

值得放大的一個瞬間：Sonnet 第一版有缺陷，審查員直接退件附具體理由，第二版修好。上一輪同位置的審查員看到同型缺陷，是寫個建議就放行的。同一個模型當審查員，合約鬆緊不同，行為完全不同——牙齒長在條文上，不長在模型上。

04一頁紙的成績

另一個極簡實驗：不要任何 skill，只有三步——Opus 讀完任務寫一頁 35 行的合約，Sonnet 照做，最後 Opus 開一個乾淨腦袋回來驗一次收。結果：功能行為全對、零 bug、$7.27（冠軍的兩成二）。

最精彩的是驗收那步：它故意弄壞 CLI 的成功訊息，發現測試沒亮紅燈——上輪害死五個組合的同款漏洞——當場自己修好、補上兩條測試。最後一道防線真的接住了球。唯一輸給完整流程的地方：有兩處接線沒釘到最深，行為是對的，但未來有人改壞時測試不一定會叫。一頁紙和全套的差距不在會不會出 bug，在保護網織得多密。

05兩類 bug 絕種了

  • 編號加一的章數缺陷：上輪十組五組中招 → 這輪三組零出現
  • 常數轉抄缺陷：三組正規表達式逐字比對全乾淨 → 零出現
  • 條文寫死＋原文照抄是結構性消滅——讓錯誤無處生長，不是賭它少發生
  • 共同舊病重申：閱讀器把資料庫編號當陣列位置的既有缺陷，三位盲評全數再度標記，修它排待辦第一位

06以後怎麼用＋帳本

情境做法代價與回報
小改動直接做，零儀式約一個小缺陷的稅
一般功能開工一頁合約＋收工一次驗收成本＋兩三成，換掉九成低級 bug
大工程／錯不起條文寫死的全套流程冠軍品質、六成價
禁忌條文鬆的全套流程最差選擇——一排綠燈的假安心

你原本的直覺「流程太重，想裸跑看看」，數據說對了一半：重不是罪，鬆才是罪。帳本：驗證輪三組 $31.57＋盲評約 $10；兩輪實驗合計約 $240。換到三種用法的實測分數，和兩類 bug 的絕種證明。
