# Harness×Model 矩陣實驗——十個 agent 團隊配置的盲評對決

2026 年 7 月 19 日，我們在一個 Rust 終端小說閱讀器專案上，讓十組不同的 agent 團隊配置做完全相同的三件開發工作，再由十位不知情的評審盲評成品。結果推翻了兩個流行直覺：花最多錢跑完整流程的配置裡，有一組墊底；被看好的單模型裸奔，輸在一個訊息字串上。

## 為什麼做這個實驗

實驗的起點是一個路線問題。市面上的開發流程 skill 多半誕生於模型能力較弱的年代：先寫五層規格、再用 Red/Green 紀律實作、每步配獨立審查。模型一代比一代強，這些為舊模型搭的鷹架照理該一層層拆掉。問題是拆哪些、留哪些，過去只有直覺，沒有數據。

我們把問題壓成一個 3×3 矩陣。流程軸有三檔：P1 原生（什麼流程都不給，做完測試要過就行）、P2 只分析（先寫完整規格再直接實作）、P3 分析加執行（規格、失敗測試先行、獨立審查、總驗收，全套紀律）。模型軸也有三檔：F（Fable 單模型從頭做到尾）、OS（Opus 規劃加 Sonnet 實作，多數工程師的日常組合）、FOS（Fable 規劃、Sonnet 實作、Opus 審查的三模型編隊）。過程中因為委派機制限制，額外多出一格 Opus 單體裸奔，湊成十組。

三件工作刻意混搭：一個藏在解析器裡的真實 bug（`&` 自選擇器在檢查前就被解析炸掉）、一個跨層功能（換源時按章節名遷移閱讀進度）、一個 TUI 體驗改善（跨書源搜尋結果摺疊）。每組拿到一字不差的驗收簡報，在獨立 git worktree 裡工作，全程寫決策日誌。評完成品的十位評審看到的是去識別副本：沒有 git 歷史、沒有規格目錄、沒有決策日誌，只有程式碼和那份簡報。

## 計分結果

評審按四個維度打分：21 條驗收標準有沒有被測試釘死、有沒有引入 bug、架構遵循度、測試殺不殺得死突變。

## 一個訊息字串，抓到五組

專案資料庫裡的章節索引 `idx` 不連續：某些站點的第一章落在 idx=1，因為 idx=0 被一個沒有連結的分卷標題佔走了。這件事寫在專案的 CLAUDE.md 裡，十組的規格作者也全都自己挖到了。可是「知道」和「每個輸出位置都做對」是兩回事。五組在使用者會看到的訊息裡寫出了「第 {idx+1} 章」，於是換源之後畫面印出「進度重置到第 2 章：第1章 起風」，同一行字自打嘴巴。

踩雷名單值得細看。Fable 單體踩了：它的測試 fixture 全部刻意用不連續的 idx，證明它完全知道這個陷阱，卻在 CLI 重置訊息裡順手加了一。Fable 規格加 Fable 實作也踩了：規格作者和實作者是同一顆心智，作者沒想到的出錯位置，實作者同樣想不到，規格淪為自己給自己的鏡子。最慘的是 p3-os：Opus 審查員在報告裡明確描述了這個缺陷，然後判了 advisory 放行，因為 Opus 自己寫的驗收條文只要求訊息包含某個子字串，審查員按字面履約，沒有越權打槍的依據。盲評把這個缺陷升級成全場唯一的 high。

避開的五組用了三種不同的辦法。p3-fos 靠審查打槍：Fable 寫的驗收條文把訊息格式釘死，Sonnet 第一輪照樣寫出 idx+1，Opus 審查員拿條文拒收，第二輪修掉，這是全實驗唯一一次重派。p2-os 靠一句警語：Opus 在規格交接裡寫了「stop using idx+1 as a chapter number」，Sonnet 讀到了、記住了、照做了。p2-fos 靠表面設計：Fable 在規格裡直接規定訊息格式「進度已遷移：{章名}」，格式裡沒有數字欄位，錯誤在結構上無處生長。p1-o 靠單一責任人的自覺：沒有人幫它兜底，它收尾前自己查了一遍。

## 墊底解剖：全套流程輸給 $4.92 的裸奔

p3-os 付了八個 agent、五十分鐘、$11.84 的成本，拿到比 $4.92 單體更差的結果。決策日誌對出三個原因。

第一是換手損耗。單體 Opus 從發現陷阱到寫出訊息全程在同一個 context 裡。p3-os 的知識要先壓縮成規格文字，再由 Sonnet 解壓，警語在壓縮時沒有升級成可斷言的條文，解壓的人寫主邏輯時記得、寫 UI 訊息時忘了。物證是第二個缺陷：簡報給定的正規表達式 `[章回節节卷]`，經過規格轉抄再到實作，變成繁體「節」重複兩次、簡體「节」消失，簡體中文書源的章號比對整條靜默失效。轉抄鏈越長，抄錯的機率越高，而單體根本沒有轉抄這一步。

第二是責任稀釋。流程裡每個角色都合理地相信別的環節會接手：實作者想「條文我都過了，審查會抓剩下的」；審查員想「條文沒禁止，按契約這是 advisory」；總驗收想「逐項審查都通過了」。三個環節各自盡職，缺陷從契約縫隙裡穿過去。單體知道自己是最後一道防線，行為就不一樣。

第三是儀式性綠燈。p3-os 走完全程時儀表板漂亮極了：三個任務全數通過審查、總驗收判定無須修補、七十九個測試全綠。每盞綠燈量測的都是條文，條文鬆，綠燈就只是心理安慰。流程給人的安全感和實際的安全，在這一組身上完全脫鉤。

## P2 的平庸與前饋的兩招

只寫規格、不設審查的三組裡，成績最好的那組其實走私了一個審查環節，把它歸位之後，純粹的「規格加實作」只剩平庸和翻車。原因在於這種配置的保護力全部發生在實作之前，屬於前饋性質，沒有任何人回頭對照成品。前饋要生效，規格作者得先把危險寫進去，這次有效的手法就兩招：警語式，把陷阱明講出來，賭實作者讀到且記住；表面設計式，把輸出格式規定死，讓錯誤沒有欄位可以表達。第二招高一個檔次，因為它把「不要犯錯」變成了「無法犯錯」。

## 三條路

十組成績排出來，可行的配置收斂成三條路。

第一條是單體全責：一個模型、零交接、自己收尾自己查。便宜、快，代價是大約一個 med 級 bug 的稅。日常中小任務走這條。

第二條是前饋設計:規格的價值濃縮成危險表面設計加條文可斷言化這兩件事，五層文件是這兩件事的昂貴包裝紙。

第三條是有牙的反饋環：前饋加獨立審查，且條文寫得足以支撐審查員拒收。這是實驗裡唯一做到零缺陷、全數釘死的配置，代價是四到六倍的成本。大型任務或錯不起的變更走這條。

卡在三條路中間的所有配置，付了儀式的錢，沒買到結構的保護。

## 動刀方向

回到起點的路線問題，答案比「流程該變輕」更精確：流程是槓桿，放大的是規格條文的品質，條文釘得死，流程把它放大成冠軍；條文鬆，流程只放大成本和縫隙。所以改革的第一刀不砍流程長度，砍條文品質：每條驗收標準必須寫成具名可斷言的值，使用者可見的文字必須規定精確格式或明列禁止項，規格裡發現的每個資料陷阱必須同時變成條文和測試錨點。第二刀把審查員的任務書換掉：與其全面重審，不如專掃沒有測試釘住的使用者可見表面，因為強模型的錯幾乎只長在那裡。第三刀才是砍儀式：設計文件降級成一張表、逐任務的上下文檔換成一段交接摘要、失敗重試上限降到一次。

實驗有邊界。三件工作對 2026 年的模型群偏簡單，十組全數達到 17 條以上釘死，天花板效應明顯；更大更難的任務可能重新拉開流程的價值差距。這份數據能定論的是中等規模、規格寫得完整的任務帶。在這個任務帶裡，數字說得很清楚：與其多開一個審查 agent，不如先把驗收條文寫到能拿來打槍。
